Tool Calling Protocol

2교시

Tool Calling은 모델이 문장 대신 Tool 이름과 JSON args로 된 호출 요청을 반환하는 기능입니다. bind_tools()는 Tool Schema를 모델에 전달할 뿐, Tool을 실행하지 않습니다.

AIMessage.tool_calls

{"name": "lookup_status", "args": {"report_id": 63}, "id": "call_1"}

ToolMessage

tool_call_id="call_1" · content='{"report_id": 63, "index_status": "fixture"}'

모델은 요청만 합니다. 허용 목록 확인, 실행, 같은 call ID로 결과를 짝짓는 일은 애플리케이션이 맡습니다.

Tool & Schema

3교시

Tool은 이름·설명·입력 Schema·반환값을 명시한 호출 가능한 기능입니다. Pydantic BaseModel로 인수 Schema를 정의하고 @tool(args_schema=...)로 연결합니다.

lookup_status.args

report_id: type: integer, exclusiveMinimum: 0

invoke({"report_id": -1})

ValidationError · Input should be greater than 0
Tool 함수는 실행되지 않습니다.

Schema는 입력 형식을 막습니다. 해당 데이터를 볼 권한은 서버가 인증된 신원으로 따로 검증합니다.

RAG as a Tool · PostgreSQL Read-only Tool

4·5교시

rag_search

Tool Wrapper(입력 검사) → E5 Embedding → pgvector → CrossEncoder Reranker → Context + LLM → status · sources

lookup_status

미리 작성한 Parameterized SELECT를 SELECT 전용 계정으로 실행합니다. LLM은 SQL을 작성하지 않습니다.

RAG 내부는 그대로 재사용합니다. sources는 실제 Context에 포함된 ID와 대조해 검증한 출처만 전달합니다. 신원(user_id)은 Tool Schema가 아니라 서버(runtime)가 주입합니다.

create_agent Integration

6교시

create_agent는 모델·Tool 목록·System Prompt를 받아 Tool 호출 → ToolMessage → 재호출 반복을 관리하는 LangChain 함수입니다.

messages Trace

요청된 tool_calls 수와 실제 ToolMessage 수를 따로 셉니다. 모델이 매번 두 Tool을 모두 고르지는 않습니다.

최종 AIMessage

Tool Call이 없는 마지막 AIMessage가 답변입니다. 출처와 상태를 따로 검증합니다.

create_agent는 반복을 관리할 뿐입니다. Tool 호출 여부는 Trace로, 답변은 별도로 확인합니다.

출처 검증

검증되지 않은 RPT-번호를 인용한 답변은 API가 반환하지 않습니다.

End-to-End: FastAPI가 신원을 인증하고 → Agent가 두 Tool을 호출하고 → 서버가 Tool 결과와 출처를 검증한 뒤 응답을 반환합니다. 다음 날 개인 프로젝트에서 이 구조를 단일 Agent·두 Tool로 연결합니다.

권한·호출 상한·출처 검증은 Prompt가 아니라 서버 코드로 강제합니다.
