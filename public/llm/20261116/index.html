01

Prompt: 무엇을 어떻게 수행할지 전달하는 입력

1 · 2교시
흐름에서질문→Context→Prompt→LLM 응답→자동 검사→근거 대조

Prompt에는 지시뿐 아니라 질문·자료·예제·출력 조건을 담을 수 있습니다. Prompt Engineering은 성공 기준을 지시로 표현하고, 결과를 비교하며 개선하는 과정입니다.

역할누구를 돕는가?
작업무엇을 수행하는가?
입력무엇을 읽는가?
제약어디까지 답하는가?
실패근거가 없으면?
출력어떤 형식으로 돌려주는가?
고정된 템플릿(Template)작업·범위·실패 기준·출력 계약
+
요청마다 바뀌는 값이번 질문 + 선택한 지식
→
완성된 Prompt모델에 전달할 입력

여섯 요소는 이 교안의 설계 틀입니다.

Zero-shot

입력→출력 예제 없이 작업과 기준을 설명합니다.

Few-shot

입력→바람직한 출력 예제를 함께 줍니다.

핵심은 문장의 화려함이 아니라 성공·실패를 확인할 수 있는 요청입니다.

02

Context: 이번 답변에 실제로 제공한 정보

3 · 4교시
흐름에서질문→Context→Prompt→LLM 응답→자동 검사→근거 대조

Context Engineering은 필요한 정보를 고르고 배치하며 출처·유효성·길이를 관리하는 일입니다. 여기서는 그중 이번 요청에 선택해 넣은 지식을 다룹니다.

101 파일 보관 ✔ 선택
102 서버 실행
103 질문 작성
→ [101]질문에 필요한 자료만 골라 ID·본문·순서를 보존해 전달합니다. 이번에 전달한 근거: “실습 파일은 개인 폴더에 보관합니다.”
“어디에 보관하나요?”필요한 사실은 위치입니다. 101의 본문에 있으므로 답과 출처를 제시합니다.answered · source_ids: [101]
“몇 년 보관하나요?”필요한 사실은 기간입니다. 본문에 없으므로 추측하지 않고 부족한 정보를 적습니다.insufficient_context · source_ids: []
입력: 지시·질문·예제·근거출력용 공간여유

Context Window는 한 번의 생성에서 다룰 문맥 길이의 한도입니다. 출력 공간도 남깁니다. 칸의 너비는 실제 비율이 아닙니다.

자료를 많이 넣는 것보다, 필요한 사실이 실제로 들어 있는지가 중요합니다.

03

출력 계약(Output Contract)과 검증(Validation): 형식과 내용은 따로 확인한다

6교시
흐름에서질문→Context→Prompt→LLM 응답→자동 검사→근거 대조

출력 계약은 응답이 따라야 할 필드·자료형·상태별 규칙입니다. 검증은 실제 응답이 정한 규칙과 근거에 맞는지 확인하는 과정입니다.

{
  "status": "answered",
  "answer": "개인 폴더에 보관합니다.",
  "source_ids": [101],
  "missing_information": ""
}

JSON은 데이터를 표현하는 텍스트 형식, Schema는 허용할 필드·자료형을 기술한 명세, Pydantic은 Python에서 데이터 구조를 선언하고 검사하는 라이브러리입니다. 정보가 부족하면 status: insufficient_context, 출처는 []로 두고 필요한 정보의 이름을 기록합니다.

1 · 문법SyntaxJSON으로 읽히는가?괄호·따옴표 등
2 · 구조Schema계약에 맞는가?필수 필드·자료형
3 · 규칙Reference · State참조·상태가 맞는가?이번에 전달한 ID·필드 조합
4 · 내용Evidence원문이 답을 뒷받침하는가?질문·주장·인용 대조
앞의 세 단계: 자동 검사마지막 단계: 사람의 근거 검토
반례101·102·103을 전달하고, 서버 실행 위치에 “프로젝트 폴더”라고 답하면서 101을 인용했습니다. 제공한 ID이므로 참조 검사는 통과하지만, 101은 파일 보관 자료이므로 근거가 맞지 않습니다.

자동 검사 통과 ≠ 답의 정확성.

04

재시도(Retry): 원인을 나누고, 멈출 조건을 둔다

7교시
흐름에서질문→Context→Prompt→LLM 응답→자동 검사→근거 대조·실패하면 입력으로 되돌아감

재시도는 응답을 다시 요청하는 일입니다. 이번 교안에서는 JSON·Schema 형식 오류만 한 번 수정 요청하며, 모든 실패를 반복하지 않습니다.

정상 답 / 정상 정보 부족자동 규칙을 통과한 응답
→
생성 종료 → 근거 검토정보 부족 판단의 적절성도 확인
JSON·Schema 오류문법·필드·자료형 문제
→
수정 1회 → 다시 검사통과하면 검토, 다시 실패하면 중단
출처·상태 규칙 위반없는 출처·모순된 조합
→
자동 재생성 없이 중단문맥과 규칙을 다시 점검
최초 응답 1회+형식 수정 1회=최대 2회

수정할 때 유지할 것은 같은 질문·문맥·출력 계약입니다. 확인된 오류만 요약해서 전달하고, 최초 응답과 수정 응답을 따로 기록합니다.

형식은 고칠 수 있어도, 재시도가 없는 근거를 만들어 주지는 않습니다.

05
