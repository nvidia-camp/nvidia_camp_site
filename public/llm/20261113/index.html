Attention은 Token 사이를 섞고 FFN은 Token마다 따로 변환한다. Residual과 LayerNorm은 층을 깊게 쌓아도 학습이 되게 돕는다. Self-Attention 하나가 Transformer 전체는 아니다.

Residual은 Attention이 아니라 기존 표현을 더하는 경로다. 실제 모델마다 Norm의 순서는 다를 수 있다.

KV Cache에서 재사용한 Key·Value이번에 계산선택된 다음 Token

고른 Token을 입력 끝에 붙여 다시 계산하고, EOS나 길이 한도에서 멈춘다. KV Cache는 이전 Token의 Key·Value를 재사용해 중복 계산을 줄인다.

KV Cache는 한 생성 과정 안의 재사용이다. 사용자 장기 Memory가 아니고, 문맥이 길수록 메모리를 더 쓴다.

유창한 출력은 사실 검증이 아니다. 정확성·권한·출처 검증은 애플리케이션이 설계한다.

RAG 경로와 답이 틀리는 네 위치

p.24 · p.80 · p.83
User Question Retriever관련 근거 찾기 Prompt + Context근거도 Token 예산에 포함 LLM다음 Token 반복 Answer + Source출처 확인
① 입력·문맥질문의 의도·필요한 제약이 빠짐
② 검색·근거관련 문서를 못 찾거나 오래된 버전 사용
③ 생성·추론근거 밖 내용을 보충하거나 오해
④ 표현·평가JSON 형식은 맞지만 내용이 틀림

RAG는 검색과 생성을 잇는 구조다. DB를 만들었다고 RAG가 되지 않고, 가져온 근거가 자동으로 참인 것도 아니다.

문제에 맞는 방법 · 정보 문제와 실행 문제

p.82 · p.84~85

정보·표현의 문제

  • Prompt: 지시·예시·출력 형식 정리
  • RAG: 외부 지식을 검색해 근거 제공
  • Fine-tuning: 모델 행동·스타일·과제 적응

실행·제어의 문제

  • Agent: 도구 선택·작업 단계 실행
  • FastAPI: 기능의 서비스 입구
  • PostgreSQL: 원본·상태·기록 저장

지식 관리 API에 이미 있는 것

  • /api/knowledge CRUD
  • PostgreSQL 원본 지식·분류
  • HTTP 오류와 DB 트랜잭션
  • 서버 재시작 후 저장 유지

LLM을 붙이면 더할 것

  • 질문 처리용 LLM 호출
  • 관련 지식 검색·Chunking·Vector DB
  • 근거·사실성 평가와 출처 관리
  • 필요하면 Agent 도구·권한·상태

RAG를 넣어도 Agent가 자동으로 생기지 않고, Fine-tuning이 사실성을 보장하지도 않는다. 실행 권한과 검증은 애플리케이션이 맡는다.

검색된 문서 속 명령 문구는 시스템 지시로 믿지 않는다(Untrusted Text). 원본 지식을 고치거나 지우면 검색 인덱스에도 반영되게 설계한다.
