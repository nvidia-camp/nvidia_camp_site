3. SQL — 실행할 DB부터 확인

SQL 파일은 pgAdmin Query Tool에서 실행합니다. VS Code의 Python 실행 버튼이나 Git Bash에 SQL 내용을 직접 넣지 않습니다. Query Tool에서 파일을 연 뒤 SQL 편집창 안에서 Ctrl+A → F5(Execute script)로 전체를 실행합니다. [pgAdmin 실행 안내]

순서연결할 DB실행할 파일·정상 결과
1. DB 생성postgres00_create_database.sql — report_agent_lab이 없을 때만. Auto-commit을 켠 새 Query Tool에서 이 파일만 실행
2. 다시 연결report_agent_lab왼쪽 Databases 새로고침 → 실습 DB 선택 → 새 Query Tool. 기존 postgres 연결 탭과 구분
3. 사전 점검report_agent_labpreflight.sql — DB 이름, UTF8, 서버 버전, vector 사용 가능 여부, 기존 테이블 확인
4. 구조 생성report_agent_labschema.sql — vector 확장 활성화, 10개 테이블·조회 VIEW 생성
5. 시드 적재report_agent_labseed.sql — 파일의 BEGIN부터 COMMIT까지 전체 실행. API 요청을 보내지 않는 상태에서 적재
6. 상태 확인report_agent_labverify.sql — SELECT 묶음별로 실행하여 아래 초기 상태와 비교

CREATE DATABASE는 트랜잭션 블록 안에서 실행할 수 없으므로 DB 생성 파일을 schema·seed와 합쳐 실행하지 않습니다. DB가 이미 있다면 생성 단계는 건너뜁니다. [PostgreSQL 규칙]

preflight에서 볼 항목

connected_database는 report_agent_lab, correct_database는 true, server_encoding은 UTF8이어야 합니다. 수업 기준은 PostgreSQL 18 계열입니다. vector_available_to_install이 true이면 서버가 vector 설치 정보를 인식합니다. schema 실행 전에는 vector_active_in_this_database가 false여도 정상일 수 있습니다.

Python의 pgvector 패키지와 PostgreSQL 서버의 vector 확장은 별도입니다. vector_available_to_install=false이면 아래 Windows 설치 항목을 확인한 뒤 다시 진행합니다. 기존 reports가 보이면 같은 Day25 DB를 이어 쓰는지 확인하며 자동 삭제하지 않습니다.

verify.sql은 여러 결과를 반환합니다. 개수·상태·무결성 검사의 각 SQL 묶음을 선택해서 실행하세요. UNION ALL 또는 WITH가 포함되면 세미콜론까지 한 묶음 전체를 선택합니다. 무결성 검사 열 error_count는 0이어야 합니다.

위 숫자는 처음 제공한 시드 상태의 기준입니다. 이미 색인한 DB에 seed를 다시 실행해도 벡터가 0으로 돌아가거나 ready가 pending으로 초기화되지 않습니다. CRUD·Prompt 버전 생성 후에는 행 수가 달라질 수 있습니다.

같은 SQL을 다시 실행하면 무엇이 유지되는가

seed는 같은 ID가 있으면 중복 삽입하거나 덮어쓰지 않습니다. 삭제되어 없는 시드 행은 다시 들어갈 수 있지만, 실습 중 수정한 내용과 추가한 데이터를 초기 상태로 복원하지는 않습니다. CREATE TABLE IF NOT EXISTS도 기존 테이블 구조를 자동 수정하는 기능이 아닙니다. 다른 구조가 남아 있다면 강사와 DB 상태를 확인합니다.

Windows PostgreSQL에 pgvector가 아직 없을 때 — 강사와 함께 준비

이미 서버에서 vector를 사용할 수 있다면 이 절은 건너뜁니다. 공식 Windows 방식은 Visual Studio의 C++ 빌드 도구를 사용합니다. VS Code와 Visual Studio C++ 빌드 도구는 다른 프로그램입니다. [공식 설치 안내]

  1. Visual Studio Installer에서 C++ 데스크톱 개발 지원과 Windows SDK를 준비합니다.
  2. 시작 메뉴에서 x64 Native Tools Command Prompt for VS를 관리자 권한으로 엽니다. 아래 명령은 Git Bash·PowerShell·pgAdmin용이 아닙니다.
  3. PostgreSQL 설치 폴더를 확인하여 PGROOT를 맞춘 뒤 실행합니다. 아래는 PostgreSQL 18 기본 경로와 확인한 pgvector v0.8.7 예시입니다.
set "PGROOT=C:\Program Files\PostgreSQL\18"
cd /d "%TEMP%"
git clone --branch v0.8.7 https://github.com/pgvector/pgvector.git pgvector_day25_087
cd pgvector_day25_087
nmake /F Makefile.win
nmake /F Makefile.win install

각 명령이 성공한 뒤 다음 명령으로 진행합니다. 폴더가 이미 있으면 무조건 삭제하지 말고 기존 준비 상태를 확인합니다. nmake를 못 찾으면 실행 창과 C++ 도구 설치를, postgres.h 오류면 PGROOT를, 접근 거부면 관리자 권한을 확인합니다. 설치 후 pgAdmin에서 preflight.sql을 다시 실행하고, 서버 파일 확인이 끝나면 schema.sql로 해당 DB의 확장을 활성화합니다.

05의 “선택”은 추가 입력 예제를 실행할지의 선택입니다. 명세의 6종 카테고리 지원 요구는 그대로입니다. 같은 등록 요청을 반복하기 전에는 앞서 생성한 데이터를 정리하세요. 환경변수에는 가장 최근 생성 ID가 저장됩니다.

실제 LLM 확인 때만 본인의 키·모델을 준비하고 allow_paid_llm을 문자열 true로 바꾸어 필요한 요청 하나를 실행한 뒤 false로 되돌립니다. skipRequest()로 건너뛴 요청은 성공 검증이 아닙니다. 해당 pre-request 기능을 지원하는 Postman을 사용합니다. [Postman 실행 제어]

생성 ID는 created_report_id에 자동 저장됩니다. 별도 report_id 환경변수를 만들지 않습니다. 정리 요청은 기록한 생성 ID만 삭제하며 시드 범위 1~180은 건너뜁니다. 생성·수정 후 GET에서는 ID뿐 아니라 제목·본문·상세값도 비교합니다.

5. 사전 준비를 학생 프로젝트에 연결

  2. 이 묶음의 common/sql/, requirements.txt, .env.example, .gitignore를 프로젝트 루트로 복사합니다. 처음이라면 .env.example을 .env로 복사하고 값을 입력합니다. 기존 실제 설정은 덮어쓰지 않습니다.
  3. PROJECT_LEVEL을 선택한 단계에 맞춥니다. 수동 검색 확인에는 이 묶음의 보완된 common/data/search_cases.json을 사용합니다.
  4. Advanced 평가를 구현하는 경우 제공한 common/data/evaluation_cases.json을 프로젝트의 tests/evaluation_cases.json으로 복사합니다. 파일은 관련 ID 참고 정답이며 평가 Python 코드는 학생이 작성합니다.

API 서버는 학생 프로젝트에서 python -m app.main으로 실행합니다. scripts/index_overviews.py도 해당 TODO를 완성한 뒤 프로젝트 루트에서 실행합니다. 이 사전 제공 폴더 자체에는 두 실행 대상이 없습니다.

검색 확인 자료 읽기

seed_catalog.json은 원문·출처 ID 참고 목록입니다. 그 안의 details는 배열이므로 항목을 그대로 POST Body로 보내지 않습니다. 요청의 details는 Postman 예시와 명세처럼 필드명이 있는 객체입니다.

search_cases.json은 5개 수동 확인 질문입니다. 문서 유형과 검색 주제는 다릅니다. “회의 결정”과 “프롬프트 버전”을 다루는 연구계획도 관련 보고서입니다. 수정한 기대 범주에는 이를 반영했고, “가중치”를 다루는 업무보고서도 포함했습니다. 제목·개요·본문을 읽고 관련성을 판단합니다.

Advanced의 evaluation_cases.json은 별도의 6개 평가 질문과 수동 관련 ID 집합입니다. 실제 예측 결과로 정답 ID를 바꾸지 않습니다. 마지막에는 검색 결과 ID를 조회·요약으로 이어서 report_id와 source_revision을 비교하고, not_found이면 요약을 호출하지 않습니다.
