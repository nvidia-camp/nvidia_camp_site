Q1첫 질문모델이 알아서 배우지 않아? 사진을 왜 미리 손봐?사진마다 크기·밝기·잡음이 제각각이고, 컴퓨터에게 사진은 아직 의미 없는 숫자다. 질문에 맞게 숫자를 바꿔 두면 규칙으로 바로 판단할 수도 있고, 모델이 배우기 좋은 입력이 되기도 한다.
전체 흐름촬영→오늘: 전처리→모델·규칙→판단
쓰임 ①규칙: 흰 영역을 보고 흠집 후보 찾기

코드에서는오늘은 cv2로 입력을 맞추고 결과 파일·요약표까지 만든다. 모델 학습은 11/05 전이학습 수업에서 한다 (p.15, 91).

Q2첫 질문사진이 어떻게 숫자가 돼? 컴퓨터는 사진 속 물체를 알아봐?카메라는 칸(Pixel)마다 들어온 빛의 세기를 0~255로 적는다. 컬러는 칸마다 숫자 3개다. 컴퓨터가 아는 것은 이 숫자뿐이라, 물체는 아직 모른다.
칸 하나B 20G 80R 2000~255 정수 (uint8)
사진 한 장240 × 320 × 3 = 230,400개 숫자강의 p.4 예
컴퓨터가아는 것: 숫자모르는 것: 흠집·글자·물체

코드에서는img = cv2.imread(path)로 읽으면 img.shape는 (240, 320, 3) 같은 세 숫자, img[y, x]는 숫자 3개다 (p.19–20).

Q3입력크기는 보통 "가로×세로"라고 하는데, 왜 shape는 (세로, 가로) 순서야?숫자 상자는 줄(행)부터 센다. "몇 번째 줄의 몇 번째 칸"이라 img[y, x]다. 반대로 resize에 주는 출력 크기는 화면처럼 가로부터 (W, H)로 적는다.
shapeH 120W 160C 3줄부터: 세로 → 가로 → 채널
dsizeW 160H 120화면 크기처럼: 가로 → 세로
퀴즈(345, 450, 3)의 450 = 가로(W)
PyTorch[N, C, H, W]채널을 앞으로 옮겨 받는다 (p.13)

코드에서는cv2.resize(img, (160, 120))의 결과 .shape는 (120, 160, 3)이다 (p.5, 31).

Q8첫 질문일부러 흐리게 만드는 게 왜 도움이 돼? 사진을 망가뜨리는 거 아냐?잡음은 한 칸만 튀는 값이라, 칸 하나만 보면 잡음인지 진짜 무늬인지 모른다. 주변 칸과 섞으면 튀는 값은 묻히고 넓은 무늬는 남는다. 이 "섞는 비율표"가 Kernel이다.

비유사진을 멀리서 보면 자잘한 얼룩은 안 보이고 큰 모양만 보인다.

1010101010010101010→(10×8 + 100) ÷ 9 = 20

넓게 섞을수록: 매끈해지지만 세부도 지워지고 계산이 는다

3×3 Kernel9번
5×5 Kernel25번
9×9 Kernel81번

출력 한 칸마다 곱하는 횟수. Day11 CNN의 합성곱과 같은 계산이다. 오늘은 사람이 Kernel 값을 정하고, CNN은 그 값을 배운다.

코드에서는cv2.GaussianBlur(gray, (5, 5), 0). (5, 5)가 Kernel 크기이고, 0은 퍼짐 정도를 Kernel 크기에서 자동으로 정하라는 뜻이다 (p.39).

Q9손잡이섞는 방법은 왜 여러 개야? (Gaussian·Median·Bilateral)튀는 점이 있을 때 평균은 흐린 점을 남기고, 가운데 값(중앙값)은 점을 없앤다. 가운데 칸이 있어야 하므로 medianBlur 크기는 1보다 큰 홀수다. Bilateral은 밝기가 많이 다른 칸을 덜 섞어 경계를 지키지만 느리다.

비유반 평균 키는 농구선수 한 명이 끼면 올라가지만, 키 순서로 줄 세운 가운데 사람의 키는 그대로다.

평균20 · 흐린 점이 남음Gaussian도 가중 평균

Q13손잡이기준값은 누가 정해? 사진마다 밝기가 다른데?조명이 고르면 사람이 정한 값 하나(Fixed)로 충분하다. 밝은 무리와 어두운 무리로 갈리면 Otsu가 그 사이 값을 스스로 찾는다. 한쪽에 그림자가 지면 Adaptive가 구역마다 다른 기준을 쓴다.
Fixed사람이 한 값조명이 고를 때 · 단순·빠름
Otsu밝은 무리 │ 어두운 무리 사이를 자동으로두 무리로 갈릴 때
Adaptive구역마다 다른 기준그림자·불균일 조명 · blockSize·C 조정
교재 본문 밖 · OpenCV 문서

코드에서는cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY + cv2.THRESH_OTSU). 기준값 자리의 0은 무시되고, Otsu가 찾은 값이 ret으로 돌아온다 (p.47).

Q14첫 질문나눴더니 자잘한 흰 점이 생겼어. 줄였다가 다시 키우면 원래대로 아냐?아니다. 주변 3×3이 모두 흰색일 때만 남기면(Erosion) 외딴 점은 통째로 사라진다. 다시 하나라도 흰색이면 칠하면(Dilation) 큰 물체만 원래 굵기로 돌아온다. 이 순서가 Opening이고, 반대 순서(Closing)는 작은 검은 구멍을 메운다.

비유지우개로 한 번 문지르면 작은 얼룩은 없어지고 큰 글씨는 얇아질 뿐이다. 다시 덧칠하면 글씨만 돌아온다.

→→
원본 → Erosion(9칸 모두 흰색일 때만 남김) → Dilation(하나라도 흰색이면 칠함) = Opening
ClosingDilation → Erosion: 물체 안 작은 검은 구멍·끊긴 글자를 메움

코드에서는k = cv2.getStructuringElement(cv2.MORPH_RECT, (3, 3)), cv2.morphologyEx(binary, cv2.MORPH_OPEN, k). 연산 전에 물체가 흰색(255)인지 먼저 확인한다 (p.50–51).

Q15확인지우고 싶지 않은 작은 점(진짜 결함)까지 사라지면?Opening은 Kernel보다 작은 흰 영역을 모두 지운다. 잡음과 결함을 크기로 구분할 수 없다면 Kernel 크기를 다시 정하고, 원본과 나란히 놓고 확인한다.
결함 1칸3×3 Kernel보다 작음 → 지워짐
결함 3칸 이상Kernel만큼 크면 → 남음
확인원본 │ 처리 후를 나란히 · 흰 Pixel 수 비교

코드에서는cv2.hconcat([binary, opened])로 나란히 저장해 보고, cv2.countNonZero로 흰 Pixel 수를 비교한다 (p.10, 53).

영상 · 같은 상자를 Frame마다5교시

Q16첫 질문영상 처리는 이미지 처리와 다른 기술이야?아니다. 영상은 사진(Frame)을 시간 순서로 이어 붙인 것이다. 한 장씩 꺼내 같은 상자를 쓰고 써넣기를 반복한다. 파일 열기·닫기는 반복 밖에서 한 번만 한다.
영상Frame 1Frame 2Frame 3…
반복read→같은 상자→write
끝ok == False → 반복 종료 → release

코드에서는ok, frame = cap.read(), if not ok: break. Frame 함수 안에서 파일을 매번 열면 느리고 자원이 샌다 (p.57, 78, 82).

Q17손잡이저장한 영상이 왜 느리게(빠르게) 재생돼?재생시간은 Frame 수 ÷ FPS다. 같은 장수라도 저장 FPS를 낮추면 길고 느리게 재생된다. 저장 FPS는 처리 속도와 상관없다.

비유플립북 48장을 1초에 12장씩 넘기면 4초, 6장씩 넘기면 8초 걸린다.

15장 ÷ 30FPS0.5초
48장 ÷ 12FPS4초
48장 ÷ 6FPS8초

코드에서는입력 FPS는 cap.get(cv2.CAP_PROP_FPS)로 읽고, 저장 FPS는 cv2.VideoWriter(path, fourcc, fps, (W, H))의 fps로 정한다 (p.8, 58–60).

Q18확인파일은 생겼는데 영상이 비어 있어Writer는 정해진 형식의 Frame만 받는다. 아래 순서로 맞춰 보고, 저장 후 다시 읽어 Frame 수를 확인한다.
①writer.isOpened() == True
②frameSize (W, H) == Frame 크기
③채널 수가 같은가 (Gray는 3채널로 바꿔서)
④확장자·코덱 조합
마지막release 후 다시 읽어 Frame 수 확인

코드에서는writer.write(cv2.cvtColor(edge, cv2.COLOR_GRAY2BGR))처럼 1채널 Edge를 3채널로 바꿔 쓴다 (p.62, 78).

증강 · train에만, 정답은 그대로6교시

Q19첫 질문사진을 일부러 뒤집거나 돌려서 넣으면 가짜 데이터 아냐?정답이 그대로인 변형이면 진짜 데이터처럼 쓸 수 있다. 새 사진을 뒤집어도 새다. 모델이 실제로 만날 다양한 방향·밝기를 미리 보여 주는 것이다.
원본새 사진정답: 새
좌우 반전새 사진 ↔정답: 새 (그대로)
밝기 +30새 사진 ☀정답: 새 (그대로)

코드에서는cv2.flip(img, 1)은 좌우, 0은 상하, 음수는 둘 다 뒤집는다 (p.66).

Q20손잡이그럼 아무 변형이나 해도 돼?아니다. 뒤집으면 정답이 바뀌는 데이터가 있다. 글자·숫자·방향 표지가 그렇다.
글자b↔d좌우 반전 ✕
숫자6↔9180° 회전 ✕
표지← 좌회전↔→ 우회전좌우 반전 ✕

코드에서는OCR·표지 데이터에서는 flip을 빼고 작은 회전·밝기 변화만 쓴다 (p.70).

Q21손잡이시험용(valid/test) 데이터에도 해야 해?아니다. 시험 문제가 매번 바뀌면 성능을 비교할 수 없다. 원본 단위로 먼저 나누고 train에만 변형을 더하며, Seed를 기록해 같은 변형을 다시 만들 수 있게 한다.
순서원본→먼저 나누기
train기본 전처리 + 무작위 증강
valid·test기본 전처리만 · 매번 같은 결과
✕시험에도 무작위 → 실행마다 점수가 달라져 비교 불가

코드에서는Seed와 변환 설정을 dict·JSON으로 남기고, 결과 파일 이름에 변환 정보를 적는다 (p.9, 71).

Q22확인사진을 돌리면 모서리는 왜 비어?회전은 "다른 자리에서" 가져오는 상자다. 출력 칸마다 원본의 어디서 왔는지 거꾸로 찾는데, 원본 밖을 가리키면 가져올 값이 없다. 그 자리는 Border 규칙으로 채운다.
2×3 행렬M = [ 회전·크기 2×2 │ 이동 2×1 ]중심·각도·Scale로 만든다
출력 칸마다출력 (x′, y′)→원본 어디?
원본 안값을 가져옴 (칸 사이면 보간)
원본 밖가져올 값 없음 → Border로 채움 (기본은 검은색)

코드에서는M = cv2.getRotationMatrix2D((w/2, h/2), 10, 1.0), cv2.warpAffine(img, M, (w, h), borderMode=cv2.BORDER_REFLECT) (p.67–68).
