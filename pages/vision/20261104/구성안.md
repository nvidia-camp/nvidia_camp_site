# Day13 개념 지도 구성안 (4판)

- **목적:** OpenCV를 처음 보는 수강생이 "컴퓨터 비전은 사진을 무엇으로 보고, 어떻게 바꿔서, 무엇을 얻는가"를 한 화면에서 이해하게 한다.
- **범위:** 강의 PDF `Day13_20261104.pdf`(93쪽) 전체.
- **수준:** 강의 3분 퀴즈 24문항을 스스로 풀 수 있는 정도. 핵심만 넣고 단순하게 쓴다.

## 1. 이야기 한 줄 (지도 맨 위)

> 카메라는 빛을 숫자 격자로 남긴다. 컴퓨터에게 그 숫자는 아직 의미가 없다. 알고 싶은 질문에 맞춰 숫자의 의미를 **밝기 → 경계 → 물체 → 모양**으로 바꿔 간다. 그 결과를 규칙이 바로 판단하거나, 모델이 배울 입력으로 넘긴다. 바꾸는 동안 무엇을 잃었는지는 원본과 비교해 확인한다.

- 근거: Szeliski 3장 도입. 오늘 배우는 처리를 "대부분의 비전 알고리즘의 첫 단계로, 사진을 이후 분석에 알맞은 형태로 바꾸는 일"이라고 설명한다.

## 2. 입력: 우리가 다루는 것은 무엇인가 (공통 바탕, 1교시)

지도에서 가장 넓은 띠다. 오늘의 모든 처리가 이 입력을 받으므로, 다섯 가지를 차례로 보여 준다.

1. **출발은 질문이다.**
   - 예: "제품에 흠집이 있나?", "문서에 어떤 글자가 있나?"
   - 질문이 정해져야 무엇을 남기고 무엇을 버릴지 정할 수 있다(강의 p.2).
2. **사진은 빛을 숫자로 적은 격자다.**
   - 카메라는 칸(Pixel)마다 들어온 빛의 세기를 0~255 숫자로 적는다. 컬러는 칸마다 숫자 3개를 적는다.
   - 그래서 사진은 `세로 × 가로 × 3` 숫자 상자 `[H,W,C]`다. OpenCV는 이 숫자 3개를 파랑·초록·빨강(BGR) 순서로 담는다(강의 p.4·18·23).
3. **컴퓨터에게 그 숫자는 아직 의미가 없다.**
   - 숫자가 말해 주는 것은 "이 칸이 얼마나 밝은가"뿐이다. 흠집인지 글자인지는 모른다.
4. **그래서 숫자의 의미를 질문 쪽으로 바꿔 간다.** 이것이 오늘 배우는 처리들이다(3절).
   - 오늘은 이 사다리의 아래쪽, 즉 판단에 쓸 단서를 만드는 단계까지 한다.
   - "이건 불량이다", "이건 고양이다" 같은 인식은 다음 수업의 모델이 한다(강의 p.15·91).
5. **영상은 사진을 시간 순서로 묶은 것이다.**
   - 사진 여러 장(Frame)에 "1초에 몇 장인가"(FPS)가 붙은 것이다(강의 p.4·55–56).

그림: 카메라 → 확대한 격자 → 한 칸 `[20,80,200]` → 숫자 상자 `[H,W,3]`. 옆에 필름 띠(영상 = 사진 묶음 + FPS)를 둔다.

## 3. 처리: 숫자의 의미를 바꾸는 사다리 (① 한 장 처리, 2–4교시)

상자 하나를 거칠 때마다 칸의 숫자가 뜻하는 것이 바뀐다. 지도의 ① 줄은 이 사다리로 그린다(강의 p.52 순서).

```
원본        칸마다 색 숫자 3개         [H,W,3] 0~255
 ↓ Gray     칸마다 밝기 1개             [H,W]   0~255     (색을 버림)
 ↓ resize   크기만 맞춤, 의미는 그대로   [h,w]
 ↓ Blur     잡음을 줄인 밝기            [H,W]   0~255     (세부가 조금 흐려짐)
 ↓ Canny    "여기가 경계인가?"          [H,W]   0 / 255
 ↓ Threshold "여기가 물체인가?"         [H,W]   0 / 255
 ↓ Morph    "물체 모양은 어떤가?"       [H,W]   0 / 255   (작은 점·구멍 정리)
```

- Canny와 Threshold는 Blur 다음에 갈라지는 두 갈래다. 경계를 원하면 Canny, 영역을 원하면 Threshold → Morph로 간다.
- 화살표마다 "앞 숫자로는 아직 답할 수 없는 것"을 한 줄로 적는다(7절).

## 4. 결과: 두 가지 쓰임 (지도 오른쪽 끝)

처리 결과는 두 곳으로 간다. 오늘 증강이 들어 있는 이유가 여기서 보인다.

- **규칙이 바로 판단한다.**
  - 사람이 기준을 정한다. 예: Threshold → Morph로 흰 영역을 정리한 뒤 개수를 세어 흠집을 찾는다.
- **모델이 배울 입력이 된다.** (다음 수업)
  - 크기를 맞추고(resize 224×224), 학습용 사진을 늘린다(증강, 6교시).
  - 같은 계산이 이어진다: Blur의 Kernel은 Day11 CNN의 합성곱과 같은 계산이다. 오늘은 사람이 Kernel 값을 정하고, CNN은 그 값을 학습한다(UDL 10.2).

## 5. 확인: 무엇을 잃었나 (아래 띠, 7·8교시)

- 처리는 언제나 무언가를 버린다. 그래서 결과를 다시 읽어 원본·설정과 대조한다.
  - **형식:** shape·dtype·채널
  - **시간:** Frame 수·FPS·재생시간
  - **개수:** 파일 수
- 원본은 덮어쓰지 않는다. 그래야 비교·재현·복구할 수 있다(강의 p.79·86).

## 6. 상자 하나 읽는 법 (카드 안 같은 틀)

상자마다 아래 다섯 줄만 둔다.

| 줄 | 내용 |
|---|---|
| 입력 → 출력 | 칸의 숫자가 무엇을 뜻하다가 무엇을 뜻하게 되나 (+ shape) |
| 참고하는 칸 | 출력 한 칸을 정할 때 입력의 어디를 보나: **자기 칸만** / **주변 칸까지** / **다른 자리에서** |
| 손잡이 → 이유 | 인자·규칙 1~3개와, 그것이 왜 필요한지 한 줄 |
| 확인할 것 | 원본과 비교해 볼 것, 잃을 수 있는 것 |
| 함수 · 강의 | 핵심 함수 한 줄 + 강의 쪽 |

- "참고하는 칸"은 상자의 복잡함 차이를 보여 준다(Szeliski 3장 구분: 3.1 자기 칸만, 3.2–3.3 주변 칸까지, 3.6 다른 자리에서).
- 영상과 증강은 새 상자가 아니라 **상자를 쓰는 방식**이다. 영상은 Frame마다 반복하고, 증강은 train에만 무작위로 쓴다.

## 7. 지도 배치

```
[이야기 한 줄]  카메라 → 숫자 → 의미 바꾸기 → 판단·모델 → 확인
┌ 입력 (1교시) ─────────────────────────────────────────────────┐
│ ① 질문  ② 빛 → 숫자 격자 [H,W,3] BGR  ③ 아직 의미 없음  ④ 영상 = 사진 묶음 + FPS │
└────────────────────────────────────────────────────────────────┘
┌ 처리: 의미 사다리 ─────────────────────────────────────┐   ┌ 결과 ───────┐
│ 2교시 [Gray][resize] ▶ 3교시 [Blur][Canny] ▶ 4교시 [Threshold][Morph] │ → │ 규칙이 판단  │
│   밝기           │       잡음↓ · 경계인가     │    물체인가 · 모양        │   │ 모델 입력    │
└──────────────────────────────────────────────────────────┘   └─────────────┘
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
 영상 5교시: 같은 상자를 Frame마다            증강 6교시: train에만, 정답이 그대로인 변형
┌ 확인 (7·8교시): 형식 · 시간 · 개수 — 무엇을 잃었나 ┐
```

- **색:** 강의 p.3을 따른다. 초록 = 색·Resize, 노랑 = Filter·Edge, 보라 = Threshold·Morphology, 연청 = 바깥 틀.

| 화살표 | 앞 숫자로 아직 답할 수 없는 것 | 굵은 숫자 |
|---|---|---|
| 2교시 → 3교시 | 밝기 숫자에는 잡음이 섞여 있다. 칸 하나만 보면 잡음인지 무늬인지 모른다 | `(100 + 10×8) ÷ 9 = 20` |
| 3교시 → 4교시 | 숫자는 여전히 "얼마나 밝은가"다. "물체인가"에는 답하지 않는다 | `T=128: 110→0, 160→255` |
| ① → 영상 | 영상도 사진 묶음이라 같은 상자를 쓴다 | `15장 ÷ 30FPS = 0.5초` |
| ① → 증강 | 정답이 그대로일 때만 바꿔 넣는다 | `b ↔ d` |

## 8. 상자 여덟 개

| 상자 | 입력 → 출력 (숫자의 의미) | 참고하는 칸 | 손잡이 → 이유 | 확인할 것 | 함수 · 강의 |
|---|---|---|---|---|---|
| Gray | 색 3개 → **밝기 1개** · `[H,W,3]`→`[H,W]` | 자기 칸만 | 가중치 0.299·0.587·0.114 → 사람이 느끼는 밝기에 가깝게 섞는 표준이라서 | 색을 버려도 질문에 답할 수 있나 | `cvtColor(img, COLOR_BGR2GRAY)` · p.27–29 |
| resize | 의미 그대로, **크기만** · `(120,160,3)` | 다른 자리에서 | 보간법 → 칸 사이엔 값이 없고(확대), 건너뛰면 계단이 생겨서(축소). `dsize=(W,H)` → 출력 크기는 가로부터 | 비율이 찌그러졌나 | `resize(img, (W,H), interpolation=INTER_AREA)` · p.30–33 |
| Blur | 밝기 → **잡음을 줄인 밝기** | 주변 칸까지 | Kernel 크기 → 넓을수록 잡음↓ 세부↓. Median → 튀는 점은 평균으로 안 지워져서. Border → 가장자리엔 이웃이 없어서 | 필요한 경계도 남았나 | `GaussianBlur(g,(5,5),0)` · p.36–41 |
| Canny | 밝기 → **경계인가** (0·255) | 주변 칸까지 | 앞에 Blur → 잡음도 경계처럼 보여서. 기준값 두 개 → 약한 경계가 끊기지 않게 | 가짜 경계·끊긴 경계 | `Canny(blur, 70, 150)` · p.42 |
| Threshold | 밝기 → **물체인가** (0·255) | 자기 칸만 | 기준값 → 예/아니오를 가를 선. Otsu·Adaptive → 사진마다, 구역마다 밝기가 달라서 | 흰색이 정말 물체인가 | `threshold(g, 128, 255, THRESH_BINARY)` · p.45–47 |
| Morph | 물체인가 → **정리된 물체 모양** | 주변 칸까지 | 순서 → 흰 점은 Opening, 검은 구멍은 Closing. Kernel 크기 → 지울 대상의 크기 | 진짜 작은 결함까지 지웠나 | `morphologyEx(b, MORPH_OPEN, k)` · p.48–52 |
| 영상 | 사진 묶음 + FPS → 같은 처리를 한 사진 묶음 + FPS | 위 상자를 Frame마다 반복 | `ok` → 끝을 알려고. FPS → 재생시간. frameSize·채널 → 저장 형식이 고정이라서 | 다시 읽어 Frame 수·FPS | `cap.read()`, `VideoWriter(..., fps, (W,H))` · p.55–62 |
| 증강 | 사진 + 정답 → 바뀐 사진 + **같은 정답** | 위 상자(뒤집기·회전·밝기)를 무작위로 | 정답 유지 → b↔d가 있어서. train에만 → 시험 조건은 고정해야 해서. Seed → 다시 만들려고 | 정답 의미가 그대로인가 | `flip(img,1)`, `warpAffine` · p.65–71 |

## 9. 질문 23개

자리는 `입력` · `왜`(상자가 필요한 이유) · `손잡이` · `확인` 중 하나다. 질문 하나는 "질문 → 한 줄 답 → (비유) → 그림 → 코드에서는" 순서로 쓰고, 비유는 ★ 네 곳에만 둔다. 질문 내용은 3판을 유지하되 입력 질문(Q1·Q2)을 2절에 맞게 고쳤다.

### 3교시 · Blur · Canny

| Q | 자리 | 질문 | 한 줄 답 | 근거 | 퀴즈 |
|---|---|---|---|---|---|
| Q8 | 왜 | 일부러 흐리게 하는 게 왜 도움이 돼? ★ | 잡음은 한 칸만 튀는 값이라 칸 하나로는 구분이 안 된다. 주변과 섞으면 튀는 값은 묻히고 넓은 무늬는 남는다(가운데 100 → 20). 섞는 비율표가 Kernel이고, Day11 CNN의 합성곱과 같은 계산이다. 넓게 섞을수록 세부도 지워지고 계산이 늘어난다(9·25·81번 곱셈) (비유: 사진을 멀리서 보면 자잘한 얼룩은 안 보이고 큰 모양만 보인다) | Sz 3.2, UDL 10.2.1, 강의 p.6·36–37 | p.44 Q3 |
