시스템 지시·질문·대화 이력·검색 근거·출력까지 예산의 일부가 된다. Context Window ≠ 영구 Memory, "많이 넣을수록 좋다"도 아님.p.32

검색 근거도 예산을 쓴다11/20 RAG에서 넣는 문서 발췌가 이 칸이다. 근거는 Token 예산에 포함되고 출처도 응답에서 확인해야 한다(p.83)
넘치면 잘린다Truncation은 Token을 잘라내는 것이며 요약이 아니다. 정보가 손실될 수 있다(p.37)
Token 수 = 시간·비용·품질길이는 응답 시간에, API 요금은 입력·출력 Token 수에 걸린다. 너무 긴 문맥은 잡음·근거 누락을 부른다(p.35)

표는 p.33의 산술 예시이며 실제 모델의 최대 길이나 과금 정책을 뜻하지 않는다.

  • Padding: 길이가 다른 문장을 한 배치로 맞춤. "AI" 뒤에 [PAD] 6개 → input_ids shape (2, 9)
  • Truncation: max_length=12를 넘는 Token은 잘린다. 이 예는 9개라 잘리지 않았다

Causal Attention 가중치를 숫자로 확인

5교시 · p.61~63
Q @ K.T/ √d_k+ Masksoftmax@ V
행 = Query(현재 위치), 열 = Key. 각 행의 합은 1, 미래 위치는 0. t1은 자기 자신만, t3는 앞쪽 2개와 자신을 함께 참고한다.

Mask가 미래 정보를 가리고, Softmax가 가중치를 만들며, V의 합성으로 출력이 된다.p.8

RAG = 근거 검색 + 생성 / Agent = 상태·도구 실행을 포함한 처리 시스템. LLM은 답을 제안할 수 있지만, 실제 실행은 Backend가 권한을 판단해야 한다.p.10

RAG를 넣었다고 Agent가 자동 완성되지 않고, Fine-tuning이 사실성까지 보장하지 않는다(p.82).

더 알아보기 · 이 페이지에서 줄인 내용
Special Token
BOS·EOS·PAD·Chat Role. 표기·ID·사용 여부는 모델·Tokenizer마다 다르다(p.30).
shape (B, T, D)
Batch · Token 수 · feature. Block을 지나도 (2, 5, 8) 그대로, LM Head에서 (2, 5, 100)(p.39, p.51, p.54).
Sentence Embedding
문장 전체를 벡터 하나로. 의미 비교·검색에 쓰며 11/18 Vector DB로 이어진다(p.40, p.45).
Cosine Similarity
벡터의 방향 유사도. [1, 0]과 [0.8, 0.2]는 0.9701, [−1, 0]과는 −1. 높아도 정답·사실성을 보장하지 않는다(p.42~43).
Position
순서 정보를 벡터 계산에 반영. Sinusoidal · Learned Position · RoPE(p.41, p.55).
Encoder · Decoder
Encoder는 대체로 양방향(분류·검색), Decoder-only는 Causal(생성), Encoder–Decoder는 번역·요약(p.49).
Multi-Head Attention
Head별로 Q·K·V를 따로 투영해 결합. 현대 LLM은 GQA/MLA 등 변형도 쓴다(p.65).
Decoding
Greedy · Temperature · Top-k · Top-p(p.75).
KV Cache
이전 Token의 Key/Value 재사용. 사용자 장기 Memory가 아니다(p.77).
사전학습 뒤 활용
Prompting(가중치 그대로) · Instruction Tuning · Preference Alignment(p.72).
