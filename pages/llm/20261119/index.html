02

Document Parsing: 형식·구조·원문 위치

2교시

Parsing은 파일 내부 구조를 해석하는 작업이고, Text Extraction은 검색에 사용할 문자열을 꺼내는 작업입니다. 문자열을 추출했다고 표·읽기 순서까지 보존된 것은 아닙니다.

UTF-8 · Unicode Transformation Format – 8-bit

Unicode 문자를 bytes로 표현하는 Encoding입니다. "가".encode("utf-8") 결과는 3bytes이고, 문자열 "가"는 한 글자입니다.

Encoding / Decoding

Encoding은 str → bytes, Decoding은 bytes → str로 해석하는 과정입니다. 서로 다른 규칙으로 읽으면 문자 오류가 발생할 수 있습니다.

형식주요 도구보존·검사할 정보
TXTbytes.decode("utf-8")인코딩 오류·빈 줄·문단
MarkdownMarkdown parserHeading Path·목록·코드 블록
HTMLBeautiful Soupmain 본문·표의 행과 열 / 메뉴 제외
PDFpypdf페이지·다단 읽기 순서·표·source_locator
Scan PDFOCR 필요 여부 판단pypdf는 이미지 속 문자를 직접 인식하지 않음

ParsedUnit의 핵심 필드

doc_id: DOC-CAREER
unit_id: page-1
page_number: 1
source_locator: career.pdf#page=1
raw_text: 추출된 페이지 텍스트

빈 추출 ≠ 스캔 확정

빈 페이지·손상·암호화·이미지 페이지 등 원인을 확인합니다. 실제로 OCR이 필요한 문서만 needs_ocr로 분류하며, 조용히 삭제하지 않습니다.

Raw File·ParsedUnit·원문 위치를 연결해야 검색한 근거를 다시 확인할 수 있습니다.

03

Text Cleaning: 형식을 정리하고 의미를 보존

3교시

Text Cleaning은 형식상의 잡음을 줄이는 작업입니다. 숫자·부정어·단위·예외 조건까지 지우는 것은 좋은 Cleaning이 아닙니다.

NFC · Normalization Form C

정준적으로 같은 Unicode 표현을 분해·재조합하는 정규화입니다. ᄀ+ᅡ → 가. 일반 본문에서 표기를 통일하는 기본 정책입니다.

NFKC · Normalization Form KC

호환 문자까지 분해·재조합해 ① → 1, ² → 2처럼 표기를 바꿀 수 있습니다. 번호·지수 의미에 영향을 줄 수 있으므로 무조건 적용하지 않습니다.

가능한 변환

"출석   안내\r\n\r\n10분  초과"
↓
"출석 안내\n\n10분 초과"

CRLF/CR을 LF로 통일하고 가로 공백을 정리하되 문단 경계를 유지합니다.

거부할 변환

원문: 제출할 수 없습니다.
오류: 제출할 수 있습니다.

부정어 삭제로 안내의 의미가 반대로 바뀌었습니다. 표·코드·TSV에도 일반 본문용 공백 규칙을 그대로 적용하면 안 됩니다.

raw_sha256

원본 파일의 bytes를 해시합니다.

clean_hash

정제된 문자열을 UTF-8로 해시합니다.

char_start/end

청크의 문자열 범위는 clean_text 기준입니다.

Offset 계약: clean_text[start:end]의 end는 제외합니다. 이 값은 PDF 화면 좌표나 원본 파일의 바이트 위치가 아닙니다.

정제 결과가 짧아졌다는 사실보다 중요한 정보가 남아 있는지 검증하는 것이 더 중요합니다.

04

Chunking: Size·Overlap·Token 한도를 함께 본다

4교시

Chunk는 문서에서 검색·Embedding에 사용하는 본문 단위입니다. 실제로는 Heading·문단·표 구조를 고려하고, 한도를 초과하는 부분만 추가로 분할합니다.

Chunk 1
[0, 40)
Chunk 2
[30, 70)
Chunk 3
[60, 71)

원문 길이

71자

청크 길이 합

91자

고유 위치 Coverage

100%

71자 본문을 Size 40, Overlap 10으로 나눈 설명용 문자 범위입니다.

Character vs Token

Size 40자는 40토큰이 아닙니다. 실제 모델의 Tokenizer를 사용해 입력 길이를 계산해야 합니다.

E5 Embedding Text

passage: [선택한 Heading] + Chunk Body

E5-small의 384차원은 출력 숫자 개수입니다. 입력 Token 상한과는 다릅니다.

Overlap을 늘릴수록 저장할 반복 내용이 늘 수 있습니다. Size는 실제 질문과 문서로 평가해야 합니다.

05

Chunk Validation · Metadata · 검색 조건

5·6교시

Chunk Validation은 문서의 일부가 어디서 왔는지, 길이·본문·위치·중복·누락이 올바른지 확인합니다. Metadata는 그 결과를 출처·버전·분류와 연결합니다.

Spanspan["text"] == clean_text[start:end]
Token Limit실제 E5 입력 전체·특수 토큰 확인
Coverage겹치는 구간은 한 번만 세기
Metadata원문·판·위치·처리 규칙·ID
20자 본문의 Chunk 구간Coverage확인할 사항
[0,8), [6,14), [12,20)100%의도한 Overlap, 전체 구간 포함
[0,8), [10,20)90%[8,10)이 누락됨
[0,8), [0,8), [8,20)100%Coverage만으로 중복 생성 오류는 못 찾음

검색 결과와 함께 보존할 Metadata

doc_id · source_version · unit_id · chunk_id
source_locator · char_start/end · pipeline_version
category · embedding_contract

필터의 순서: 정확 검색에서는 대상 범위(WHERE category = ... 및 공개 버전)를 제한한 뒤, 해당 범위에서 거리 기준 Top-k를 반환합니다. 전체 Top-k를 구한 뒤 필터링하면 다른 결과가 나올 수 있습니다.

Coverage 100%도 원본 PDF의 완전한 추출이나 Chunk의 의미 보존을 보증하지 않습니다.

06

pgvector Indexing · Version Publish · Basic RAG 연결

7·8교시

18일의 E5-small(384차원) + pgvector를 그대로 사용해 Chunk를 저장합니다. 같은 입력은 중복 증가 없이 재실행하고, 새 판은 검증 전까지 공개하지 않습니다.

staging새 source_version·pipeline_version으로 Chunk·Vector 준비
readySpan·모델 계약·저장 개수·원문 연결 검사 통과
publish짧은 Transaction에서 현재 공개 포인터 전환

성공: v2로 전환

가상 사례에서 v1이 A·B·C이고 v2가 A·B라면 공개 후 검색은 v2의 A·B만 반환해야 합니다. 실습 DOC-ATTEND v1·v2는 각각 2청크이며 이전 버전 제외를 검증합니다.

current_version = 'v2'
current_pipeline_version = 'ingest-e5-v1'

실패: 기존 정상 버전 유지

v2의 Embedding·검증·저장 중 실패가 나면 이전 공개 포인터를 유지합니다. 실행 실패를 원문 삭제로 취급하지 않습니다.

20일의 Retriever 계약: chunk_id·body·source_locator·source_version과 검색 상태를 반환합니다. 16일 KnowledgeAnswer.source_ids가 정수 목록이므로 필요한 경우 별도의 정수 출처 ID 매핑을 명시합니다.

좋은 인덱싱은 검색 성공뿐 아니라 재실행·버전 변경·부분 실패 뒤의 데이터 일관성까지 설명할 수 있어야 합니다.
