4. 데이터 모델 · 전체 ERD 한 장으로 확인

4.1 전체 ERD (10개 테이블 · 73개 컬럼)

아래 ERD 하나에 실제 테이블명, 모든 컬럼, 자료형, PK/FK, UNIQUE, NOT NULL, DEFAULT, CHECK와 참조 관계를 표시했습니다. 필요한 정보를 다른 그림이나 컬럼 사전에서 찾을 필요가 없습니다. HTML에서는 전체 보기 / 원본 크기 / 확대 버튼으로 확인합니다.

ERD를 확대해 모든 컬럼과 제약조건을 읽으세요.

읽기 순서: report_categories → reports → 해당 종류의 상세 테이블 1개와 report_embeddings → Prompt인 경우만 prompt_versions. PK/FK/NN/DF/CK 등의 약어, 허용 코드, 교차 테이블 검증 규칙은 ERD 하단에 함께 명시했습니다. 저장되는 물리 테이블은 10개이며 추가하지 않았습니다.

5. 초기 데이터 및 제공 SQL 규격

실습 ZIP 별도 제공 파일: sql/schema.sql(DDL, vector(384), FK, 인덱스), sql/seed.sql(반복 가능한 초기 데이터 INSERT), scripts/index_overviews.py(수강생이 구현 또는 강사 시연 후 실행). seed.sql은 벡터를 가짜 상수로 채우지 않는다.

테이블 제공 데이터 적재 방법
report_categories 6행 seed.sql: 정의된 카테고리가 6개라 30개를 만들지 않음
reports 180행 카테고리당 30개, 각 개요와 전역 식별자
상세 테이블 6종 각 30행 = 180행 종류에 맞는 report_id 1:1; 제목·본문·작성자·시각 포함
prompt_versions 60행 Prompt 30개 × v1/v2. 활성 버전은 v2; 이력은 유지
report_embeddings 180행 시드 SQL 이후 E5 실제 Embedding 일괄 생성
합계 606행 시드 SQL 완료 426행 + 인덱싱 완료 180행

예외: report_categories는 정의된 6종만 두며, 향후 운영 로그·검수결과 테이블은 인위적으로 30행을 만들지 않는다. 180개 보고서의 벡터도 실제 E5를 실행해야만 180행이 된다.

샘플 데이터 품질: 가중치, 결측치, 전처리, 모델 성능, 프롬프트 버전, 회의 결정 등 서로 다른 검색 주제; 관련어·유사어·무관어 테스트 세트; 본문은 100~1000자 수준의 구체적이고 서로 다른 한국어 내용. 개요는 본문을 대표해야 하며 단순 ID만 바꾼 반복 문장은 금지.

적재 순서: CREATE EXTENSION vector 점검 → DDL → seed.sql(카테고리·reports·상세·prompt_versions) → E5 실제 개요 임베딩 180개 → 384차원·정상 상태 검증. 시드는 ON CONFLICT 등으로 중복 실행 시 행 수 증가 없이 재현되도록 작성; 기존 Day24 테이블을 DROP하지 않음.

검증 SQL에 포함할 항목: 총 보고서 180, 상세 title/content/author 유효성, create_at/update_at 시간 순서, 카테고리별 30, 상세 6종 각각 30, Prompt 버전 60, 벡터 180, vector_dims(embedding)=384, 누락 FK 0, 최신 revision/인덱스 불일치 0.

6. HTTP API 계약 — 이 절만 보면 구현·테스트 가능

공통 계약: Prefix /api/v1(Health는 /health), 요청/응답은 JSON, 모든 시각은 UTC ISO 8601, 식별자는 양의 정수. Postman으로 검증한다. GET·DELETE에는 JSON Body가 없고, 아래에 Path 및 Query Parameter를 별도로 명시했다. DB의 create_at·update_at는 API에서는 created_at·updated_at으로 반환한다. 예시 ID·유사도·LLM 문장은 형식을 설명하기 위한 값이다.

  "title": "가중치 적용에 따른 분류 모델 실험",
  "author": "김연구",
  "content": "실험 조건을 통일하고 클래스 가중치에 따른 성능 변화를 비교했다.",
  "overview": "클래스 불균형 데이터에서 가중치 적용이 분류 성능에 미치는 영향을 분석한 보고서",

    "experiment_date": "2026-11-19",

Prompt 생성 예외: content는 details.prompt_text와 같아야 하며, 처음 등록할 때 prompt_versions에 v1을 동시에 생성한다. 다른 카테고리는 해당 상세 테이블에 한 행을 생성한다.

  • 응답 201:

  • 오류: 422 범위·형식·카테고리·필수 필드 위반, 503 실제 Embedding 실패, 500 DB 실패. 보고서+상세 행+Vector를 같은 성공/실패 단위로 처리한다. 181은 예시값이며 실제 ID는 DB가 부여한다.

API-04 · Title 부분 검색·목록 조회

GET/api/v1/reportsBasic
  • 요청 예: GET /api/v1/reports?title=가중치&limit=20&offset=0.
  • Query: title(선택 문자열; 없으면 전체), limit(선택 정수, 기본 20, 1~100), offset(선택 정수, 기본 0, 0 이상). JSON Body 없음.
  • Intermediate 선택: category_code=EXPERIMENT, updated_after=2026-11-01T00:00:00Z 필터. 기본 정렬: 상세 테이블의 update_at DESC, report_id DESC.
  • 응답 200:
{"items":[{"report_id":12,"category_code":"EXPERIMENT","title":"가중치 실험","revision":1}],"total":1,"limit":20,"offset":0}
  • title은 대소문자 비구분 포함 검색. 0건이면 items:[], total:0, HTTP 200. 검색 파라미터는 바인딩·LIKE 특수문자 처리를 한다.

API-05 · 보고서 전체 수정

PUT/api/v1/reports/{report_id}Basic

  • Body (기존 종류의 필드 전체 교체; category_code는 변경 불가):
{
  "title":"가중치 실험 — 재분석","author":"김연구",
  "content":"변경된 조건을 반영해 성능을 재분석했다.",

API-07 · Keyword + Semantic 유사도 검색

POST/api/v1/search/similarBasic
  • 요청: POST /api/v1/search/similar.
  • Body:
{"query":"가중치","category_code":null,"keyword_limit":20,"semantic_limit":20}
  • query: 공백 제거 후 1~200자 필수; category_code: 선택(문자열 또는 null); keyword_limit·semantic_limit: 선택 정수, 기본 20, 범위 1~100. Category 필터는 양쪽 후보군에 동일하게 적용.
  • Keyword: 제목·Overview·본문 포함 검색, Semantic: E5 query: 임베딩과 개요 벡터 간 거리(<=>). 준비되지 않은 인덱스 또는 오래된 Revision은 제외한다. report_id로 중복 제거하고, Keyword가 있으면 먼저 고려, 없으면 설정된 유사도 임계값을 통과한 후보를 고려한다. 동점은 낮은 report_id 우선. 반드시 1건 또는 없음.
  • 응답 200 (발견):
{"status":"found","query":"가중치","best_match":{"report_id":12,"title":"클래스 가중치 실험","category_code":"EXPERIMENT","overview":"클래스별 성능 비교","keyword_match":true,"cosine_similarity":0.82}}
  • 응답 200 (미발견): {"status":"not_found","query":"존재하지 않는 개념","best_match":null}.
  • 0.82는 가상 수치. 검색 임계값은 .env의 SEARCH_MIN_SIMILARITY(초기 후보 0.75)로 설정하고 관련·무관 평가 데이터로 검증한다. Intermediate에서 점수·후보선택 근거·필터 강화. not_found는 HTTP 오류가 아니다.

API-08 · LLM 보고서 요약

POST/api/v1/reports/{report_id}/summarizeBasic
  • 요청: POST /api/v1/reports/12/summarize; Path: report_id=12.
  • Body:
{"style":"brief","max_sentences":3}
  • style: Basic은 brief, Intermediate는 brief|structured; max_sentences: 선택, 기본 3, 1~10. RDB 상세 content 전체에서 근거만 추출해 요약하고, 원문을 새로운 시스템 지시로 실행하지 않는다.
  • 응답 200:
{"report_id":12,"source_revision":1,"summary":"실험은 클래스 가중치 적용 전후를 같은 데이터 분할로 비교했습니다. Macro-F1과 소수 클래스 재현율의 변화를 기록했습니다.","model":"configured-llm-model","status":"completed"}
  • Structured 모드는 purpose,key_points,conclusion,limitations를 검증한다. 미존재 404, API 연결 실패 503, Timeout 504. Mock 요약을 실제 LLM 성공으로 표시하지 않는다.

API-09 · Agent 동작 실행

POST/api/v1/agent/runBasic
  • 요청: POST /api/v1/agent/run; Body는 수행할 작업에 따라 아래 서로 다른 JSON 중 하나를 사용한다.
{"action":"get_report","report_id":12}

{"action":"find_report","query":"가중치"}

{"action":"summarize_report","report_id":12}
  • Intermediate: {"action":"search_and_summarize","query":"가중치"}. 검색 성공 시 원문 요약, 미발견이면 LLM 호출하지 않음.

{"action":"find_report","status":"completed","tool_calls":["find_similar_report"],"data":{"status":"found","best_match":{"report_id":12,"title":"가중치 실험"}}}
  • 필수 report_id·query 누락 또는 미지원 Action은 422. Basic은 search_and_summarize와 LLM Tool Calling을 구현하지 않아도 합격이다. Basic의 명시적 action 분기는 자율 Agent가 아닌 결정적 도구 라우팅이다.

6.2 공통 오류 응답 형식

{"error":{"code":"REPORT_NOT_FOUND","message":"요청한 보고서를 찾을 수 없습니다.","details":{}}}
HTTP 상태 적용 예시 오류 코드
400 잘못된 작업 의미 등 별도 검사에서 거절 INVALID_ACTION
404 ID·Prompt 버전 등 리소스 없음 REPORT_NOT_FOUND 등
409 Advanced의 낙관적 잠금 충돌 REVISION_CONFLICT
422 필수값·카테고리·details·Action 검증 실패 VALIDATION_ERROR, NOT_PROMPT_REPORT
500 DB 내부 오류(비밀·SQL 미노출) INTERNAL_ERROR
503 Embedding·LLM·DB 연결 실패 EMBEDDING_UNAVAILABLE, LLM_UNAVAILABLE
504 LLM/API Timeout LLM_TIMEOUT

FastAPI 기본 422 응답 형식은 위 사용자 정의 오류 형식과 다르다. Basic에서는 기본 Pydantic 422를 허용하고 Intermediate 이상에서 공통 Error Handler를 구현한다. 유사도 not_found는 HTTP 200이다.

7. 기능 요구사항 및 난이도별 체크리스트

모든 ID는 테스트·추적에 활용할 고유 요구사항 ID다. Basic 수강생은 B-*, Intermediate 수강생은 B-* + I-*, Advanced 수강생은 B-* + I-* + A-*를 목표로 한다. 전체 체크리스트를 모두 수행해야 한다는 의미는 아니다.

7.1 Basic — 최소 완성 흐름

요구사항 ID 체크 구현 내용 및 완료 기준 관련 API/테이블
B-01 ☐ 명세와 공통 구조에 따라 FastAPI 실행. /docs, /health 정상 API-00
B-02 ☐ DB 세션·ORM 연결, 제공된 DDL 실행, 6개 분류 확인 categories, reports
B-03 ☐ 180개 보고서·6종 상세 30개씩·Prompt 버전 60개 시드 데이터 확인 seed.sql
B-04 ☐ 카테고리 6건 조회, 미등록 코드 거부 API-01
B-05 ☐ 공통 보고서 Create + 해당 종류의 상세 1행, Transaction Commit/Rollback API-02
B-06 ☐ ID 단일 조회, 존재/미존재 200/404 API-03
B-07 ☐ 제목 부분 일치 목록, 페이징·빈 결과(200 빈 배열) API-04
B-08 ☐ 보고서 전체 수정·Revision 증가·상세행 갱신 API-05
B-09 ☐ 보고서 삭제 후 원문·상세·벡터 참조 제거 API-06
B-10 ☐ E5 passage:/query: 및 384차원 개요 인덱싱 180개 report_embeddings
B-11 ☐ 생성·Overview 수정·삭제 시 Vector 반영, 실패 시 이전 상태 유지 API-02/05/06
B-12 ☐ Keyword+Semantic 후보 결합, 최고 1건 또는 not_found API-07
B-13 ☐ 원문 DB 조회 후 실제 LLM API로 요약; ID/호출 실패 구분 API-08

Basic 우선 개발 순서: B-01~04·B-06/07(환경·시드 조회) → B-10의 E5 어댑터 → B-05/08/09(CRUD) → B-10 일괄 색인·B-11/12 → B-13~15. 등록 전에 encode·encode_overview를 준비하고, 초기 개요 180건의 일괄 색인은 검색 전에 실행한다. 최종 목표는 B-15까지이며, 진도에 따라 완료 범위와 미완료 내용을 기록한다.

7.2 Intermediate — 응용 및 데이터 계약 검증

요구사항 ID 체크 구현 내용 및 완료 기준
I-01 ☐ Category별 Detail Pydantic 모델 검증, 유효성·404·409/422 구분
I-02 ☐ Title·Category·수정일 필터, 정렬·페이징, SQL 파라미터 안전성
I-03 ☐ Keyword 점수와 Semantic 점수 분리 및 선정 근거 제공
I-04 ☐ not_found 평가 세트로 threshold·오탐 점검. 검색 필터 동일 적용
I-05 ☐ Overview 변경에 따른 재임베딩, 본문만 변경 시 불필요한 재연산 방지
I-06 ☐ Prompt 버전 추가/목록 조회, 불변 이력 유지
I-07 ☐ 구조화 LLM 요약(목적·핵심·결론·한계) Pydantic 검증
I-08 ☐ Agent search_and_summarize 구현; 미검색 시 LLM 호출하지 않음
I-09 ☐ API 오류·모델 오류에 대한 계약 테스트 및 반환 형식 점검

7.3 Advanced — 현업 안정성·도구 호출

요구사항 ID 체크 구현 내용 및 완료 기준
A-01 ☐ expected_revision 기반 동시 수정 충돌 409 및 무손실 처리
A-02 ☐ failed/pending 재색인 API·상태 전이·조회 제외·복구·중복 재실행
A-03 ☐ Prompt 활성 버전 변경과 prompt_reports.content 동기화, 이전 버전 보존
A-04 ☐ LLM Tool Calling: 허용 3개 Tool, 스키마 검증, 최대 호출 3회, 안전한 종료
A-05 ☐ LLM 429/5xx/Timeout 재시도·예산·토큰 소비 요약(비밀/원문 로그 제외)
A-06 ☐ 검색 평가 세트와 Recall@k, false positive/negative 사례·threshold 분석
A-07 ☐ Transaction Rollback·삭제 후 검색 제외·stale vector 회귀 테스트
A-08 ☐ 구조화 실행 로그·Agent Run 조회·실패 분류(PII/비밀 비저장)
A-09 ☐ DB/키/모델 장애 시 사용자에게 안전한 오류 응답, 운영 절차 작성

필수 기능 범위는 앞서 합의된 범위를 따르되, 체크리스트 세분화는 실제 개발자가 확인할 단위에 맞춘다. Intermediate·Advanced는 선택적 도전 범위이며 수강생별 완료 수준을 분리 평가한다.

8. 검증 시나리오·합격 기준

이번 개정의 추가 검증: 6개 상세 테이블 각각에 title, content, author, create_at, update_at가 존재해야 한다. 모든 행의 작성자·제목·본문은 공백이 아니며 update_at >= create_at가 성립해야 한다. GET 응답의 created_at·updated_at는 DB의 해당 상세 행 create_at·update_at 값과 같다. ID·Title·Hybrid 검색은 동일한 report_id를 반환해야 한다.

TC ID 난이도 실행 절차 기대 결과
T-01 B 시드 적재·각 테이블 COUNT 6 카테고리, 180 보고서, 상세 6×30, Prompt 60
T-02 B index_overviews.py 인덱싱 실제 180개 384차원 벡터, 모두 ready
T-03 B 실험 보고서 POST → GET 같은 title/content/author/overview/details, 상세 1개, create_at/update_at 존재
T-04 B title 가중치 부분 검색 관련 보고서 목록, total/페이지 정상
T-05 B query 가중치 유사도 검색 관련 보고서 1건(시드 Ground Truth 목록과 비교)
T-06 B 무관 질문 검색 판정 기준 미달 시 HTTP 200 / status not_found
T-07 B overview 수정 후 재검색 이전 벡터 대신 새 개요를 반영, revision 일치
T-08 B 삭제 후 ID 조회·검색 ID 404 / 검색에서 제외, Detail/Vector 정리

12. 설계 근거와 주의사항

  1. 이전 Day24 실습에서 검증된 E5/pgvector 조건(intfloat/multilingual-e5-small, 384차원, query: /passage: , 실제 모델과 Mock 구분)을 재사용. Day24의 ingest_* 테이블을 재사용·삭제하는 것이 아니라 이번 프로젝트의 report_* 데이터 모델을 별도로 만든다.
  2. 이번 과제는 보고서 한 건의 개요 벡터 하나가 검색 대상이므로 Day24의 ParsedUnit→Chunk 파이프라인을 모든 보고서에 필수 적용하지 않는다. 이전에 배운 기술을 잊지 않도록 선택 심화 과제로 Chunking/재색인을 응용할 수 있으나 하루 범위에서는 제외.
  3. pgvector는 PostgreSQL 내부에서 vector(384)를 저장하고 Cosine Distance <=>를 제공한다. SQLAlchemy는 DB Transaction의 Commit/Rollback을 관리한다.
  4. Basic의 명시적 action 라우팅을 LLM 자율 Agent와 동일시하지 않는다. 11월 20일 프로젝트에서는 Tool 역할 분리와 요청·응답 계약을 먼저 학습하고 Advanced에서 제한된 Tool Calling을 다룬다.
  5. 검색의 의미상 정확성은 데이터·질문·임계값에 의존하므로 “가중치 검색은 무조건 report_id=12”처럼 임의 고정하지 않는다. 샘플 데이터 제작 시 정답 보고서 후보 ID를 테스트 데이터에 별도 기록한다.

공식 참고: pgvector GitHub https://github.com/pgvector/pgvector, SQLAlchemy 2.0 Session https://docs.sqlalchemy.org/en/20/orm/session_basics.html, SentenceTransformers E5 모델 카드 https://huggingface.co/intfloat/multilingual-e5-small. 최신 공식 API 동작에 대한 추가 검증은 시연 코드 작성 시 진행한다.

부록 A. 범위 및 용어 해석

  • 사용자가 말한 보고서 종류는 6종: 실험 결과 보고서, 일일 업무 보고서, 연구 계획서, 데이터 처리 보고서, 프롬프트, 회의록.
  • Basic/Intermediate/Advanced는 서로 다른 프로젝트가 아니다. 동일한 API·ERD·최종 현업형 구조를 향해 구현 범위와 시작 조건만 다르다.
  • pgvector는 별도 서버가 아닌 PostgreSQL 확장이다. report_embeddings만 벡터 타입 vector(384)를 사용한다.
  • Overview(검색용 개요): 보고서를 찾기 위한 10~1000자 텍스트로 사용자가 생성·수정 요청에 포함한다. 보고서 전체 원문과 다르다.
  • Summary(LLM 요약): 해당 종류의 상세 보고서 테이블에 저장된 현재 content를 LLM API로 요약한 결과. Basic에서는 요청 시 생성하며 별도 테이블에 영속 저장하지 않는다.
  • Keyword Search: 제목·개요·본문의 텍스트 포함 검색. Semantic Search: query: 검색어와 passage: 개요의 E5 유사도.
  • Hybrid Search: Keyword와 Semantic 후보를 결합해 한 건 또는 not_found 반환하는 기능. 전문 형태소 분석이나 BM25는 이번 필수 범위가 아니다.
  • Agent: Basic의 명시적 action 분기 → Intermediate의 search→summary 결합 → Advanced의 제한된 LLM Tool Calling. 자유로운 자동 삭제 기능은 허용하지 않는다.
  • 보고서의 실제 저장 위치: reports는 전역 ID·분류·Overview·Index 상태·Revision만 보유한다. title, content, author, create_at, update_at는 6개 상세 테이블 각각에 실제 컬럼으로 저장한다. 같은 필드를 reports에 복제하지 않는다.
  • DB 컬럼명과 API 필드명: DB는 요청한 create_at, update_at, author를 사용한다. API에서는 기존 계약의 created_at, updated_at으로 직렬화한다(명시적 alias).
