## 2. 큰 그림

### 2-1. 어제 · 오전 · 오후 · 다음

```text
Day18 SQL·트랜잭션  →  오전: FastAPI(JSON 파일) 따로, SQL(PostgreSQL) 따로  →  오후: 둘을 연결  →  다음: LLM·RAG (이 DB가 원본 지식)
```

오전에는 API를 호출해도 DB가 바뀌지 않았다. 오후에는 API 요청 하나가 DB의 행 하나로 이어진다.

### 2-2. 오전과 오후, 바뀐 것은 저장하는 곳 하나

| | 오전 | 오후 |
|---|---|---|
| 주소·Method·입력·응답 | `/api/knowledge` 다섯 개 | **그대로** |
| 저장하는 곳 | `data.json` 파일 | PostgreSQL `day19_crud_b`의 두 테이블 |
| id를 정하는 쪽 | 코드의 `next_id` | **DB** (IDENTITY) |
| 분류(category) | 문자열 그대로 저장 | 문자열 → `categories` 테이블의 id(`category_id`)로 바꿔 저장 |

### 2-3. 요청 하나가 지나가는 길 (실제 값)

POST 한 번이 DB 행이 되기까지. 이 그림이 페이지 전체의 지도이고, 아래 세부가 이 그림의 칸을 하나씩 채운다.

```text
① 요청      POST /api/knowledge
            {"title":"가상환경 정책","content":"새 프로젝트는 uv로 가상환경을 만듭니다.","category":"policy"}
② FastAPI  KnowledgeWrite가 세 필드를 검사 (빈 값·길이 초과면 여기서 422, DB까지 가지 않음)
③ Session  get_db()가 이 요청 전용 Session 하나를 열어 함수에 넘김
④ ORM      "policy"를 categories에서 찾음 → 없음 → Category 추가, flush → id 4
            Knowledge(title, content, category_id=4) 추가, flush → id 5
⑤ commit   두 INSERT를 함께 확정
⑥ 응답      201 {"title":"가상환경 정책", ..., "category":"policy", "id":5}
⑦ 확인      SQL: SELECT ... WHERE k.id = 5  →  5 | 가상환경 정책 | ... | policy   (같은 행)
```

### 2-4. 오늘 처음 나오는 이름 네 개

교재가 "같은 기능의 다른 이름이 아니다"라고 강조한 네 개. 페이지에서는 ②~⑤ 그림 옆에 둔다.

| 이름 | 한 줄 뜻 | 오늘 코드에서 |
|---|---|---|
| Engine | DB 연결을 만들고 재사용하는 기반. 앱에 하나 | `create_engine(settings.database_url)` |
| Driver (Psycopg) | Python과 PostgreSQL 사이에서 실제로 통신하는 라이브러리 | URL의 `postgresql+psycopg` |
| ORM Model | 테이블 하나를 Python 클래스 하나로 적은 것. 행 하나 = 객체 하나 | `class Knowledge(Base)` |
| Session | 요청 하나의 DB 작업 공간. 객체를 모았다가 SQL로 보내고, 확정(commit)하거나 취소(rollback)한다 | `db: Session = Depends(get_db)` |

### 2-5. 단계 지도 (= 페이지 목차)

| 묶음 | 단계 | 키워드 |
|---|---|---|
| 1 연결 | 1 접속 설정 · 2 Session · 3 ORM Model · 4 첫 조회 | `.env`, `URL.create`, `get_db`, `select` |
| 2 CRUD | 5 분류 연결 · 6 POST · 7 GET 상세 · 8 PUT · 9 DELETE | `add`, `flush`, `commit`, `db.delete` |

# app/settings.py
class Settings(BaseSettings):
    db_user: str
    db_password: str
    db_host: str = "localhost"

#### 2. Session · 요청마다 하나 열고, 끝나면 닫는다 (TODO B02)

- 한 줄 뜻: Dependency(`Depends`)는 "이 함수를 부르기 전에 먼저 준비할 것". `get_db()`가 Session을 열어 넘겨주고, 응답이 나가면 닫는다.

```python
# app/db.py
engine = create_engine(settings.database_url, pool_pre_ping=True)   # 앱에 하나
SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)

def get_db():
    with SessionLocal() as db:   # 요청이 들어오면 열고
        yield db                 # 함수에 넘겨주고
                                 # 응답이 나가면 with가 닫는다
```

- 핵심: Engine은 앱에 하나, Session은 요청마다 하나. 닫는 것(close)은 저장(commit)이 아니다.

#### 3. ORM Model · 테이블을 클래스로 (제공 코드, 읽기만)

- 한 줄 뜻: 어제 SQL로 만든 두 테이블을 Python 클래스로 적는다. 클래스를 적는다고 테이블이 새로 만들어지지는 않는다.

```python
# app/models.py
class Category(Base):
    __tablename__ = "categories"
    id: Mapped[int] = mapped_column(BigInteger, Identity(always=True), primary_key=True)
    name: Mapped[str] = mapped_column(String(30), unique=True)

class Knowledge(Base):
    __tablename__ = "knowledge"
    id: Mapped[int] = mapped_column(BigInteger, Identity(always=True), primary_key=True)
    title: Mapped[str] = mapped_column(String(80))
    content: Mapped[str] = mapped_column(Text)
    category_id: Mapped[int] = mapped_column(ForeignKey("categories.id"))
    category: Mapped[Category] = relationship()   # item.category.name으로 분류명을 읽는다
```

- 결과(외부 표현과 내부 표현): API 응답은 `"category": "policy"`, DB 행은 `category_id = 4`. 같은 지식 id 5다.
- 핵심: API는 분류를 **이름**으로, DB는 **번호**로 주고받는다. 이 둘을 바꾸는 것이 오늘 코드의 절반이다.

#### 4. 첫 조회 · SQL로 넣은 지식이 API에 보인다 (TODO B03)

### 묶음 2 · CRUD (2교시)

#### 5. 분류 연결 · 이름으로 찾고, 없으면 만든다 (TODO B04)

```python
def get_or_create_category(db, name):
    category = db.scalar(select(Category).where(Category.name == name))
    if category is None:
        category = Category(name=name)
        db.add(category)
        db.flush()      # INSERT를 보내 id만 받아 둔다. 아직 확정 아님
    return category
```

- 결과: `learning` → 기존 id 1 재사용. `policy` → 없어서 새로 만들고 id 4.
- 한 줄 뜻: `add`는 Session에 올려 두기, `flush`는 SQL을 DB에 보내 id 받기, `commit`은 확정. (10단계에서 실측으로 비교)

#### 6. POST · 저장하고 201 (TODO B06)

```python
@app.post("/api/knowledge", response_model=KnowledgeRead, status_code=201)
def create_knowledge(payload: KnowledgeWrite, db: Session = Depends(get_db)):
    with transaction(db):                                   # 끝나면 commit (11단계)
        category = get_or_create_category(db, payload.category)
        item = Knowledge(title=payload.title, content=payload.content, category=category)
        db.add(item)
        db.flush()                                          # DB가 id를 발급
        result = to_read(item)
    return result
```

- 결과: A `learning` → 201, id 4 / B `policy` → 201, id 5. SQL로 id 5를 찾으면 같은 행.
- 핵심: 오전의 `next_id`가 사라졌다. id는 DB가 정한다.

### 묶음 3 · 트랜잭션 (3교시)

#### 10. flush와 commit · 언제 다른 사람에게 보이나

- 같은 앱 코드로 Session 하나에서 지식을 추가하면서, **다른 연결**에서 행 수를 셌다.

| 이 Session에서 | `item.id` | 다른 연결에서 본 knowledge 수 |
|---|---|---|
| `db.add(item)` | None | 5 |
| `db.flush()` | 7 | **5** (아직 안 보임) |
| `db.commit()` | 7 | **6** |

- 핵심: flush 뒤에 id가 생겨도 아직 확정이 아니다. 다른 요청에게는 commit해야 보인다. 그래서 201 응답은 commit이 성공한 뒤에 보낸다.

#### 11. 함께 확정 · 새 분류만 남는 반쪽 저장 막기 (TODO B09)

```python
@contextmanager
def transaction(db):
    try:
        yield            # with 안의 add·flush를 실행하고
        db.commit()      # 모두 성공하면 한 번에 확정
    except Exception:
        db.rollback()    # 하나라도 실패하면 전부 취소
        raise
```

- 실험: 새 분류를 만든 뒤, 지식 저장이 DB 규칙(본문 2,000자 이하)에 걸려 실패하게 했다.

| 저장 방식 | 지식 | 새 분류 |
|---|---|---|
| 분류 먼저 commit, 그다음 지식 | 실패 | **남음** (지식 없는 분류) |
| `with transaction(db):` 안에서 함께 | 실패 | **없음** (함께 취소) |

- 핵심: 함께 맞아야 하는 변경은 commit 한 번으로 묶는다. 어제 배운 BEGIN·COMMIT·ROLLBACK이 코드에서는 이 열 줄이다.

#### 12. 실패한 요청은 DB를 바꾸지 않는다

| 요청 | 응답 | knowledge 수 | categories 수 |
|---|---|---|---|
| (시작) | | 5 | 4 |
| POST, `content=""` | 422 | 5 | 4 |
| PUT `/5`, content만 보냄 | 422 | 5 | 4 |
| PUT `/9999`, 새 분류 `brandnew` | 404 | 5 | 4 (`brandnew` 0건) |

- 핵심: 422는 FastAPI가 입력을 보고 거절한 것(DB까지 가지 않음), 404는 찾아보고 없어서 멈춘 것(새 분류도 안 만듦).

### 묶음 4 · Migration (4교시)

#### 13. ORM만 바꾸면 · DB는 따라오지 않는다

- 실험: `Knowledge` 클래스에 `source` 열을 적기만 하고 조회했다.
- 결과: 조회 실패 (`column knowledge.source does not exist`)
- 핵심: 클래스는 DB의 설계도를 **읽는** 쪽이다. 실제 테이블을 바꾸려면 Migration이 필요하다.

#### 14. Revision 적용 · Alembic (TODO M01·M02)

- 한 줄 뜻: Migration = 테이블 구조 변경을 순서 있는 파일(Revision)로 남기고 DB에 적용하는 것. Alembic은 SQLAlchemy용 Migration 도구.
- 주 DB(`day19_crud_b`)는 건드리지 않고 연습 DB `day19_migration_b`에서만 한다.

```python
# migrations/versions/002_source.py
revision = "002_source"
down_revision = "001_initial"          # 바로 앞 Revision

def upgrade():
    op.add_column("knowledge", sa.Column("source", sa.String(120), nullable=True))

def downgrade():
    op.drop_column("knowledge", "source")
```

| 명령 | 결과 |
|---|---|
| `alembic current` | (없음) |
| `alembic upgrade 001_initial` | categories·knowledge 생성, current `001_initial` |
| 기준 지식 1건 INSERT | id 1 `기준 지식` |
| `alembic upgrade head` | `source` VARCHAR(120) NULL 허용 열 추가, current `002_source (head)` |
| 기존 행 | id 1 그대로, `source`는 NULL |
| `alembic downgrade 001_initial` | `source` 열 삭제, 행 1건 유지 |

- 핵심: 새 열은 NULL 허용으로 추가해야 기존 행이 깨지지 않는다. downgrade는 그 열의 값을 함께 지운다.

SELECT k.id, k.title, k.content, c.name AS category

## 4. 종합 · 일일프로젝트 A 유지 · B 수정 · C 삭제

시작 N = 3 → POST A·B·C (id 4·5·6) → PUT B → 실패 요청 3개 → DELETE C → 서버 종료 후 재시작 → GET

| | 재시작 뒤 API | SQL |
|---|---|---|
| A (4) | 200, 그대로 | 있음 |
| B (5) | 200, 수정한 본문 | 있음 |
| C (6) | 404 | 0행 |
| 전체 | 5건 = N+2 | 5행 |

네 줄 정리:

1. API 약속(주소·입력·응답)은 오전과 같고, 저장하는 곳만 PostgreSQL로 바뀌었다.
2. 요청 하나에 Session 하나. 그 안에서 add·flush로 모으고, commit 한 번으로 확정하거나 rollback으로 함께 취소한다.
3. API는 분류를 이름으로, DB는 번호(FK)로 다룬다. 바꾸는 일은 `get_or_create_category`와 `to_read`가 한다.
4. 테이블 구조를 바꾸는 일은 ORM 코드가 아니라 Migration(Revision 적용)이 한다. 성공은 응답 id로 DB 행을 다시 찾아 확인한다.

## 5. 더 알아보기 · 넣지 않는 것

접힌 "더 알아보기":

- rollback해도 발급된 id 번호는 돌아오지 않는다 (10단계에서 id 6이 지워진 뒤 7이 나온 이유)
- 오류 종류별 응답: DB 규칙 충돌 409, DB 연결 실패 503, 그 밖 500
- `refresh()`, `close()`가 하는 일과 하지 않는 일
- autogenerate는 초안이라 검토가 필요하고, `stamp`는 DDL을 실행하지 않는다
- intermediate·advanced가 더하는 것: 파일 분리(`schemas.py`), Router·Service·Repository 구조, 테스트 DB와 `dependency_overrides`

넣지 않는 것: 실습 진행 장치(probes·recovery·`verify_link.py` 실행 방법), 오류 메시지 원문 전체, `.gitignore` 세부, pgAdmin 조작(PostgreSQL 가이드 링크), 평가 배점, 시간 배분.

1. **설명 깊이.** 사용자 기준 "처음 보는 사람도 이해"를 위해 단계마다 "한 줄 뜻"을 넣고, 큰 그림에 2-3 "요청 하나가 지나가는 길"을 실제 값으로 둔다. 이 정도면 충분한지, 단계마다 "왜 이렇게 하나" 한 줄을 더 둘지.
