실습 1 · FastAPI

문제 하나를 풀고 저장한 뒤 /docs에서 눌러 보기를 반복합니다.

진행 순서

  1. VS Code로 01_FastAPI 폴더를 열고 설치합니다. 
    python -m pip install -r requirements-check.txt
  2. 서버를 켜고 http://127.0.0.1:8000/docs를 엽니다. main.py를 저장할 때마다 서버가 다시 켜집니다. 
    python -m uvicorn main:app --reload
  3. /docs에서 API를 펼치고 Try it out → Execute. 아직 안 푼 문제면 500이 나오고, 서버 터미널에 문제 번호가 나옵니다. 
    NotImplementedError: B-API-01: 주석 요구사항을 완성하세요.
  4. 그 문제의 raise NotImplementedError(…) 줄을 지우고 TODO 주석대로 코드를 씁니다. 저장 후 다시 Execute.
  5. 6개를 다 풀면 다른 터미널에서 채점합니다. 
    python check_api.py
    검사 통과: 40개 확인 / B / 임시 데이터만 사용
    덜 풀었으면 검사 실패: NotImplementedError: B-API-02처럼 다음 문제를 알려 줍니다.

문제

문제할 일/docs에서 확인
API-01entries를 id 오름차순으로 반환GET 목록
API-02id가 같은 항목을 반환GET 2
API-03요청 Body를 dict로, next_id를 id로POST
API-04목록에 추가, next_id +1, 저장
API-05찾은 위치의 항목을 교체하고 저장PUT 4
API-06찾은 위치의 항목 하나만 삭제하고 저장DELETE 4

문제를 풀며 생각해 볼 점

  • id와 목록 위치는 다릅니다. 찾을 때는 entry["id"]로, 바꾸거나 지울 때는 찾은 위치 i로 합니다.
  • 바꾼 뒤 저장해야 남습니다. write_data(data)를 부르지 않으면 서버를 다시 켰을 때 사라집니다.
  • next_id는 줄이지 않습니다. 삭제해도 그대로 두어야 새 항목의 id가 겹치지 않습니다.
  • 상태 코드가 결과를 말합니다. 생성 201, 삭제 204(본문 없음), 없는 id 404를 데코레이터와 예외가 정합니다.

실습 2A · DB 구축

빈 DB day19_build_b에 categories와 knowledge 테이블을 만듭니다.

진행 순서

  1. pgAdmin에서 Databases 우클릭 → Create → Database로 day19_build_b, day19_crud_b 두 개를 만듭니다. 파일 맨 위 안전장치가 DB 이름을 확인하므로 이름을 정확히 씁니다.
  2. day19_build_b 우클릭 → Query Tool → 폴더 아이콘으로 A_구축/build.sql을 엽니다.
  3. 문제 4개를 풀고 전체 실행(F5). 안 푼 문제가 있으면 그 이름이 오류에 나옵니다. 
    ERROR:  syntax error at or near "__TODO_B_DDL_01__"
    오류가 나면 ROLLBACK;만 선택해서 실행한 뒤 고쳐서 다시 실행합니다.
  4. check_structure.sql, check_insert.sql을 차례로 열어 실행합니다.

문제

문제할 일
DDL-01categories.id를 자동 번호(IDENTITY)와 PRIMARY KEY로
DDL-02분류 이름 1~30자 CHECK
DDL-03제목 1~80자, 본문 1~2000자 CHECK 2개
DDL-04category_id가 categories(id)를 참조, 부모 삭제는 RESTRICT

문제를 풀며 생각해 볼 점

  • id는 누가 정하나요? GENERATED ALWAYS AS IDENTITY는 DB가 번호를 발급하고, INSERT에서 id를 직접 넣지 못하게 합니다.
  • 제약조건에 이름을 붙이는 이유는 위반했을 때 오류에 그 이름이 나와 어떤 규칙인지 바로 알 수 있어서입니다. 명세의 이름을 그대로 씁니다.
  • FK는 자식이 부모를 가리킵니다. knowledge(자식)의 category_id가 categories(부모)의 id를 가리킵니다. RESTRICT는 지식이 남아 있는 분류를 지우지 못하게 합니다.
  • FK는 연결 규칙입니다. 두 테이블을 합쳐 보여 주는 것은 조회할 때 쓰는 JOIN입니다(2B의 R03).

이런 화면이 나오면 됩니다

정답 코드 보기 (build.sql)
DDL-01
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
DDL-02
CONSTRAINT categories_name_length CHECK (char_length(name) BETWEEN 1 AND 30)
DDL-03
CONSTRAINT knowledge_title_length CHECK (char_length(title) BETWEEN 1 AND 80),
CONSTRAINT knowledge_content_length CHECK (char_length(content) BETWEEN 1 AND 2000),
DDL-04
REFERENCES public.categories(id) ON DELETE RESTRICT

실습 2B · CRUD

완성된 DB day19_crud_b에서 조회·추가·수정·삭제 SQL을 씁니다.

진행 순서

  1. day19_crud_b Query Tool에서 B_CRUD/00_ready_database.sql을 한 번 전체 실행합니다. 지식 3개가 준비됩니다.
  2. B_CRUD/tasks.sql을 엽니다. 파일 전체를 실행하지 않습니다. 문제를 풀고, 실행할 문장만 드래그해서 선택한 뒤 F5를 누릅니다.
  3. R01~R04는 SELECT 하나씩. C01·U01·U02·D01은 BEGIN; → 변경문 → COMMIT; 또는 ROLLBACK; → SELECT를 한 줄씩 실행합니다.
  4. C01 INSERT 결과의 id를 적어 두고, 뒤 문제의 __NEW_ID__를 그 숫자로 바꿉니다. 처음 한 번이면 4입니다.
  5. 결과 표를 CRUD_명세와_예상결과.md와 비교합니다. 마지막으로 errors.sql을 구간별로 실행합니다.

문제

문제할 일결과
R01id 오름차순 정렬3행
R02id가 2인 행만“서버 실행”
R03두 테이블을 잇는 JOIN 조건분류 이름이 붙은 3행
R04분류별 지식 수2 · 1 · 0
C01새 행 INSERT새 id 4
U01수정 후 ROLLBACK원래 문장
U02수정 후 COMMIT바뀐 문장
D01추가한 행 DELETE처음 3행

문제를 풀며 생각해 볼 점

  • 순서는 ORDER BY가 정합니다. 없으면 DB가 돌려주는 순서는 보장되지 않습니다.
  • JOIN 조건은 FK 열과 PK 열입니다. 2A에서 만든 연결(category_id → id)을 조회에 씁니다.
  • LEFT JOIN에서 무엇을 세나요? 지식이 없는 reference가 0이 되려면 COUNT(*)가 아니라 지식 쪽 열을 셉니다.
  • 새 id는 DB가 정합니다. RETURNING으로 받아서 다음 문제에 씁니다.
  • 같은 UPDATE라도 끝이 다르면 결과가 다릅니다. ROLLBACK은 취소, COMMIT은 확정입니다.
