실습 1 · FastAPI

문제 하나를 풀고 저장한 뒤 /docs에서 눌러 보기를 반복합니다.

진행 순서

  1. VS Code로 01_FastAPI 폴더를 열고 설치합니다. 
    python -m pip install -r requirements-check.txt
  2. 서버를 켜고 http://127.0.0.1:8000/docs를 엽니다. main.py를 저장할 때마다 서버가 다시 켜집니다. 
    python -m uvicorn main:app --reload
  3. /docs에서 API를 펼치고 Try it out → Execute. 아직 안 푼 문제면 500이 나오고, 서버 터미널에 문제 번호가 나옵니다. 
    NotImplementedError: B-API-01: 주석 요구사항을 완성하세요.
  4. 그 문제의 raise NotImplementedError(…) 줄을 지우고 TODO 주석대로 코드를 씁니다. 저장 후 다시 Execute.
  5. 6개를 다 풀면 다른 터미널에서 채점합니다. 
    python check_api.py
    검사 통과: 40개 확인 / B / 임시 데이터만 사용
    덜 풀었으면 검사 실패: NotImplementedError: B-API-02처럼 다음 문제를 알려 줍니다.

문제

문제마다 함수 안에 이미 준비된 변수가 있습니다. 그 변수로 할 일만 씁니다.

문제함수쓸 수 있는 변수할 일
API-01list_knowledgedataentries를 id 오름차순으로 return
API-02get_knowledge
for 문 안		entry knowledge_identry의 id가 knowledge_id와 같으면 entry를 return
API-03create_knowledgepayload datapayload를 dict로 바꿔 entry를 만들고, next_id를 entry의 id로
API-04entry dataentries에 추가 → next_id 1 증가 → write_data(data)
API-05update_knowledge
id를 찾은 뒤		i updated dataentries의 i번째를 updated로 바꾸고 저장
API-06delete_knowledge
id를 찾은 뒤		i dataentries의 i번째 하나만 지우고 저장

문제를 풀며 생각해 볼 점

  • id와 목록 위치는 다릅니다. 찾을 때는 entry["id"]로, 바꾸거나 지울 때는 찾은 위치 i로 합니다.
  • 바꾼 뒤 저장해야 남습니다. write_data(data)를 부르지 않으면 서버를 다시 켰을 때 사라집니다.
  • next_id는 줄이지 않습니다. 삭제해도 그대로 두어야 새 항목의 id가 겹치지 않습니다.
  • 상태 코드가 결과를 말합니다. 생성 201, 삭제 204(본문 없음), 없는 id 404를 데코레이터와 예외가 정합니다.

이런 화면이 나오면 됩니다

/docs에서 Execute를 누른 뒤의 Server response 부분입니다.

API-01 · 목록 반환

main.py › list_knowledge

받은 코드

    with LOCK:
        data = read_data()
    # TODO B-API-01: data의 entries를 id 오름차순으로 반환하세요. sorted(..., key=lambda e:
    # e["id"])를 사용할 수 있습니다. next_id는 응답하지 않습니다.
    raise NotImplementedError("B-API-01: 주석 요구사항을 완성하세요.")

푼 코드

    with LOCK:
        data = read_data()
    # TODO B-API-01: …
    return sorted(data["entries"], key=lambda e: e["id"])
  1. TODO 주석을 읽습니다. 할 일(entries를 id 오름차순으로 반환)과 힌트(sorted(..., key=…))가 함께 있습니다.
  2. 위에서 준비된 변수를 찾습니다. data는 {"next_id": 4, "entries": [...]} 모양입니다.
  3. raise 줄을 지우고 그 자리에 씁니다. BEGIN·END 주석은 그대로 둡니다.
  4. /docs에서 GET /api/knowledge를 Execute → 500이 200으로 바뀝니다.

API-02 · id로 하나 찾기

main.py › get_knowledge

받은 코드

    for entry in data["entries"]:
        # TODO B-API-02: 반복 중인 entry의 id가 knowledge_id와 같을 때
        # entry를 반환하세요. 목록 인덱스와 ID를 혼동하지 마세요.
        raise NotImplementedError("B-API-02: …")
    raise HTTPException(404, "Knowledge not found")

푼 코드

    for entry in data["entries"]:
        # TODO B-API-02: …
        if entry["id"] == knowledge_id:
            return entry
    raise HTTPException(404, "Knowledge not found")
  1. 빈칸이 for 문 안에 있습니다. 항목 하나(entry)를 볼 때마다 실행됩니다.
  2. 목록 위치가 아니라 entry["id"]를 비교합니다. 삭제가 있으면 위치와 id가 달라지기 때문입니다.
  3. 못 찾으면 for 문이 끝나고 아래 404가 실행됩니다. 404는 이미 써 있습니다.
  4. /docs에서 GET 2는 200, 999999는 404가 나오면 됩니다.

이제 직접 API-03~06도 같은 방법입니다. 함수 안에 준비된 변수(payload, entry, i, updated)를 찾고, 바꾼 뒤에는 write_data(data)로 저장합니다. 마지막에 python check_api.py로 채점합니다.

실습 2A · DB 구축

빈 DB day19_build_b에 categories와 knowledge 테이블을 만듭니다.

진행 순서

  1. pgAdmin에서 Databases 우클릭 → Create → Database로 day19_build_b, day19_crud_b 두 개를 만듭니다. 파일 맨 위 안전장치가 DB 이름을 확인하므로 이름을 정확히 씁니다.
  2. day19_build_b 우클릭 → Query Tool → 폴더 아이콘으로 A_구축/build.sql을 엽니다.
  3. 문제 4개를 풀고 전체 실행(F5). 안 푼 문제가 있으면 그 이름이 오류에 나옵니다. 
    ERROR:  syntax error at or near "__TODO_B_DDL_01__"
    오류가 나면 ROLLBACK;만 선택해서 실행한 뒤 고쳐서 다시 실행합니다.
  4. check_structure.sql, check_insert.sql을 차례로 열어 실행합니다.

문제

문제는 __TODO_…__ 자리입니다. 그 자리만 바꾸고 앞뒤 코드는 그대로 둡니다.

문제빈칸 모양채울 것
DDL-01id BIGINT ▢,자동 번호(IDENTITY)와 PRIMARY KEY 키워드
DDL-02CHECK (▢)name 길이가 1~30자인지 보는 조건식
DDL-03CHECK (▢), × 2title 1~80자, content 1~2000자 조건식
DDL-04REFERENCES ▢가리킬 테이블(열)과 부모 삭제 규칙 RESTRICT

길이 조건과 이름은 스키마명세서.md의 표에 그대로 있습니다.

문제를 풀며 생각해 볼 점

  • id는 누가 정하나요? GENERATED ALWAYS AS IDENTITY는 DB가 번호를 발급하고, INSERT에서 id를 직접 넣지 못하게 합니다.
  • 제약조건에 이름을 붙이는 이유는 위반했을 때 오류에 그 이름이 나와 어떤 규칙인지 바로 알 수 있어서입니다. 명세의 이름을 그대로 씁니다.
  • FK는 자식이 부모를 가리킵니다. knowledge(자식)의 category_id가 categories(부모)의 id를 가리킵니다. RESTRICT는 지식이 남아 있는 분류를 지우지 못하게 합니다.
  • FK는 연결 규칙입니다. 두 테이블을 합쳐 보여 주는 것은 조회할 때 쓰는 JOIN입니다(2B의 R03).

이런 화면이 나오면 됩니다

  2. B_CRUD/tasks.sql을 엽니다. 파일 전체를 실행하지 않습니다. 문제를 풀고, 실행할 문장만 드래그해서 선택한 뒤 F5를 누릅니다.
  3. R01~R04는 SELECT 하나씩. C01·U01·U02·D01은 BEGIN; → 변경문 → COMMIT; 또는 ROLLBACK; → SELECT를 한 줄씩 실행합니다.
  4. C01 INSERT 결과의 id를 적어 두고, 뒤 문제의 __NEW_ID__를 그 숫자로 바꿉니다. 처음 한 번이면 4입니다.
  5. 결과 표를 CRUD_명세와_예상결과.md와 비교합니다. 마지막으로 errors.sql을 구간별로 실행합니다.

문제

SQL은 대부분 써 있고 빈칸은 키워드나 조건 하나입니다.

문제빈칸 모양채울 것결과
R01FROM knowledge ▢ id;정렬 키워드3행
R02FROM knowledge ▢ id = 2;조건 키워드“서버 실행”
R03JOIN categories AS c ON ▢두 테이블을 잇는 조건식분류 이름이 붙은 3행
R04SELECT c.name, ▢ AS knowledge_count분류별 지식 수를 세는 식2 · 1 · 0
C01▢ public.knowledge(title, …)추가 명령새 id 4
U01·U02▢ public.knowledge SET …수정 명령 (둘 다 같음)원래 / 바뀐 문장
D01▢ public.knowledge WHERE …삭제 명령처음 3행

__NEW_ID__는 빈칸이 아닙니다. C01 결과의 id(처음이면 4)를 넣는 자리입니다.

문제를 풀며 생각해 볼 점

  • 순서는 ORDER BY가 정합니다. 없으면 DB가 돌려주는 순서는 보장되지 않습니다.
  • JOIN 조건은 FK 열과 PK 열입니다. 2A에서 만든 연결(category_id → id)을 조회에 씁니다.
  • LEFT JOIN에서 무엇을 세나요? 지식이 없는 reference가 0이 되려면 COUNT(*)가 아니라 지식 쪽 열을 셉니다.
  • 새 id는 DB가 정합니다. RETURNING으로 받아서 다음 문제에 씁니다.
  • 같은 UPDATE라도 끝이 다르면 결과가 다릅니다. ROLLBACK은 취소, COMMIT은 확정입니다.

C01 · 추가하고 새 id 받기

B_CRUD/tasks.sql › CASE C01

받은 코드

BEGIN;
-- TODO B-SQL-05: … 행을 INSERT하고 id·title·category_id를
-- RETURNING하세요. 실제 id를 기억합니다.
__TODO_B_SQL_05__ public.knowledge(title,content,category_id)
VALUES ('보충 학습','복습 자료는 개인 폴더에서 확인합니다.',1)
RETURNING id,title,category_id;
COMMIT;
SELECT COUNT(*) AS knowledge_count FROM public.knowledge;

푼 코드

BEGIN;                               -- ① 이 줄만 실행
INSERT INTO public.knowledge(title,content,category_id)
VALUES ('보충 학습','복습 자료는 개인 폴더에서 확인합니다.',1)
RETURNING id,title,category_id;   -- ② 여기까지 실행 → id 4
COMMIT;                              -- ③ 이 줄만 실행
SELECT COUNT(*) …;                    -- ④ 개수 4
  1. 빈칸은 추가 명령 하나(INSERT INTO)입니다. 열과 값은 이미 써 있습니다.
  2. ①~④를 따로따로 선택해서 실행합니다. 한꺼번에 실행하면 마지막 개수만 보여서 새 id를 놓칩니다.
  3. ②에서 나온 id(처음이면 4)를 적어 둡니다. 뒤 문제의 __NEW_ID__를 모두 이 숫자로 바꿉니다.

이제 직접 R02~R04는 R01처럼 빈칸에 키워드나 조건을 넣고 SELECT 하나씩 실행합니다. U01·U02·D01은 C01처럼 BEGIN → 변경문 → ROLLBACK 또는 COMMIT → SELECT를 한 줄씩 실행하고, 아래 사진과 결과를 비교합니다.
